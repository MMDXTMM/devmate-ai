# 多轮项目 Agent、SSE 与 MCP 设计

## 1. 目标与分阶段边界

DevMate 要同时服务两类使用者：

- 浏览器用户通过“向项目提问”进行有上下文的中文项目理解；
- 外部 AI 客户端未来通过 MCP 调用 DevMate 的只读项目证据能力。

两个协议不能混为一谈：浏览器回答流使用业务 SSE；MCP 使用 Spring AI MCP Server 的 Streamable HTTP。后者是独立的工具协议，不复用页面的 `messages/stream` 接口，也不采用已经被 Streamable HTTP 替代的旧 MCP SSE transport。

当前闭环已经完成“多轮对话 + 每轮 Hybrid RAG + Spring AI 流式调用 + 浏览器 SSE”。MCP Server 仍是下一闭环，当前文档不得把计划写成已实现能力。

## 2. 当前已实现链路

```text
登录用户选择已解析项目
  → 创建固定 revision/provider/model/promptVersion 的对话
  → 提交问题与 UUID v4 attemptKey
  → 校验项目成员和对话归属
  → 使用本用户同版本成功报告定位业务代码；无匹配时使用 Hybrid RAG
  → 短事务写入 USER/ASSISTANT(RUNNING)
  → 独立线程调用 Spring AI ChatClient.stream()
  → SSE 输出 message/evidence/token/done/failed
  → 短事务保存最终回答或可读失败
  → 下一轮携带最近已完成消息并重新检索证据
```

模型只负责基于消息历史和本轮证据生成中文回答。Java 服务负责权限、revision 固定、证据检索、消息顺序、并发控制、幂等、超时、持久化和错误脱敏。

## 3. HTTP 契约

普通接口继续使用统一响应：

- `POST /api/projects/{projectId}/agent-conversations`
- `GET /api/projects/{projectId}/agent-conversations`
- `GET /api/projects/{projectId}/agent-conversations/{conversationId}/messages`

流式接口为：

- `POST /api/projects/{projectId}/agent-conversations/{conversationId}/messages/stream`
- `Content-Type: text/event-stream`
- 请求包含 `question` 和小写 UUID v4 `attemptKey`

事件含义：

- `message`：服务端已创建回答消息并返回字符串 ID、模型和状态；
- `evidence`：本轮命中的文件、符号、行号和有限代码片段；
- `token`：模型增量文本；
- `done`：已持久化的完整回答；
- `failed`：可读失败，不包含 SQL、Key、Prompt 或模型原始响应。

浏览器使用 `fetch` 读取 SSE，而不是 `EventSource`，因为该请求需要 POST JSON 和账户 JWT。用户关闭弹窗会中止浏览器读取，但服务端任务仍会完成持久化，避免消息永久停在 `RUNNING`。

## 4. 状态、幂等与失败

- 对话固定项目 revision 和模型快照；源码版本变化后必须新建对话。
- `(conversation_id, attempt_key)` 防止网络重试重复调用模型；相同 key 对应不同问题返回冲突。
- `running_key=conversation_id` 的唯一约束保证一个对话同一时刻只有一个生成任务。
- 会话行锁串行分配 `sequence_no`，数据库唯一键作为最终一致性保护。
- 模型调用和 SSE 发送不在数据库事务内；只有开始、完成和失败状态使用短事务。
- 模型 429、网络错误、空回答、超长回答和任务队列拒绝均保存或返回可读状态。
- 只持久化证据 Chunk ID；历史回读时由 Java 重新校验并回填真实路径、行号和代码片段。

## 5. 下一闭环：只读 MCP Server

下一闭环采用 Spring AI WebMVC MCP Streamable HTTP Server，第一版只暴露四个受控只读工具：

1. `get_project_overview`：返回项目版本、技术栈和业务地图摘要；
2. `search_project_code`：在固定项目/revision 内执行 Hybrid RAG；
3. `get_symbol_context`：按合法 Chunk/Symbol 返回有限源码上下文；
4. `get_review_findings`：读取已保存的静态或 AI 审查结论。

MCP 参数不能决定账户、任意文件路径、数据库、Shell 或外部 URL。服务端必须从认证上下文固定用户身份，校验项目成员关系，并对输出做字符预算、源码裁剪和审计。第一版不提供写文件、运行命令、修改代码、提交 Git 或创建付费审查任务的 MCP Tool。

MCP 闭环的验收标准是：受信任客户端能发现四个工具；有权限项目可查询；越权项目、伪造 revision、非法 Chunk 和超预算请求被拒绝；所有工具均有正常、失败和权限测试。


## 7. 浏览器失败恢复与阅读体验（2026-11-11）

- 打开对话自动读取历史；推荐问题只预填，不能自动消耗额度。
- 状态显示为中文，模型围栏代码块以文本形式放入 `pre/code`，源码及 HTML 字符均转义显示。
- 提交失败恢复原问题，提供“不调用模型”的历史刷新；未知断线结果复用同一请求幂等键，最终事件丢失时查询服务端持久化状态，不把断线直接判为模型失败。
- 正在回答时禁止切换或新建对话，关闭会中止浏览器读取；不同项目/视图的延迟结果不覆盖当前消息。
- 这批修改没有实现 MCP Server，相关能力仍以第 5 节的计划为准。

## 8. 真实流式服务兼容与认证修复（2026-11-11）

- 实际兼容服务的结束包含 `finish_reason/message` 而没有 `delta`，Spring AI 1.1.8 会丢失结束元数据并记录空指针。仅对管理员配置的兼容服务，将这种结束包转换为空增量，保留结束原因和用量；不再次拼接末包完整文本，也不容忍未结束的非法数据包。
- JWT 校验成功后把身份保存到当前请求属性，由 Spring Security 在 ASYNC/ERROR 内部转发时读取，修复回答已保存但 SSE 连接无法正常结束的问题。仍为无 Session 认证，不放行匿名转发；原始请求的身份与项目权限检查继续执行。
- 回归测试使用本地 HTTP SSE 数据复现协议差异；开启真实安全配置的 MockMvc 测试覆盖结束转发、未登录 401 和跨账户 403。

## 9. 项目聊天工作台与渐进阅读（2026-11-11）

- 项目工作台及“业务与源码”页均可进入项目聊天。每条 AI 业务流程增加“让 AI 讲解这条业务”，只预填问题，由用户发送；进入聊天历史本身不要求模型已配置或当前可连接。
- 侧栏列出当前账号、当前项目最近 50 段对话，支持标题搜索、更新时间与模型展示。消息仍保存到现有 `conversation/conversation_message`，页面不另存一份聊天正文，关闭或刷新后从后端恢复。
- 历史、回答区各自滚动；向上阅读时新文字不强制滚回底部，提供“回到最新消息”。输入框固定在底部，Enter 发送、Shift+Enter 换行；中文输入法确认候选时不误发送。
- Spring AI/SSE 提供真实增量，前端按 Unicode 码点逐步显示，并对拥挤的增量队列加速跟进；最终回答以服务端保存内容为准，等待当前显示队列结束后切换为历史消息，避免重复或跳变。尊重系统减少动态效果设置；切换项目、关闭和卸载时清除显示队列。
- 展示“查找代码 → 组织回答 → 逐字输出”状态；关闭窗口只停止浏览器读取，后台仍会生成并保存。围栏代码、标题、列表、加粗、行内代码均以安全文本组件显示，不解释模型 HTML，不是完整 Markdown 引擎。
- SSE 解析覆盖 CRLF 被分割到多个网络包、UTF-8 中文被逐字节分割和非 SSE 成功响应，并释放 reader 锁。

## 10. 从业务名称定位代码与清楚回答

- `conversationSeeds` 只读取当前用户、当前项目、固定 revision 的最新成功报告；较新的失败报告不会掩盖该成功记录。报告只作为检索线索，不作为代码事实。
- 依据该项目真实报告中的流程名称、接口标识匹配中文双字片段或英文标识，不内置“工单/商城/优惠券”等业务翻译或预写答案。概览问题优先取每条流程的一处代表性证据，再补支撑代码，最多 6 个种子。
- 引用 ID 先经既有项目/revision 证据回填校验，再交给带种子的词法与调用关系检索；匹配不到报告业务时保持 Hybrid RAG。既有检索数量和 Token 预算继续生效，没有换用外部向量数据库或额外付费的查询翻译模型。
- “它、继续、刚才”等追问会携带上一轮用户主题参与检索，模型仍接收最近的已完成聊天消息。每轮证据编号独立，历史编号不能直接当作本轮事实引用。
- 新建对话默认 `project-conversation-v2`：先直接回答，再解释“谁使用、做什么、如何走完一条业务”，具体流程说明接口、校验、数据和失败，技术名称放在解释之后。证据不足时简短指出缺失并给出下一步，不反复堆叠“无法确认”。旧 v1 对话保持原提示词契约和全部历史，可新建对话使用 v2。
- 这仍依赖报告覆盖和源码证据；不能保证任何自然语言问题都命中，也没有宣称静态代码等同真实运行验证。

## 11. 本轮验证

自动化通过后端 210 项、前端 97 项测试、TypeScript/Vue 构建和差异空白检查。新增检查覆盖业务主题匹配、账号与版本隔离、失败报告回退、多轮主题继承、历史恢复、逐字队列、断开清理、中文输入法、跨包 SSE 和安全排版。

在当前联调账号及公司兼容 API 上，经 Vite 5174 代理完成两轮真实提问：首轮约 2.9 秒开始 token，14 秒完成；第二轮约 3.6 秒开始、26 秒完成。均与所问业务报告的 5 条代码证据重合，保存 4 条消息，重读一致，相同 attemptKey 重放无新增消息。没有据此宣称模型准确率。浏览器工具访问限制仍在，本轮没有实际页面点击、滚动或布局验收。
