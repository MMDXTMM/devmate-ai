# DevMate AI 项目总设计

## 1. 项目定位

**中文名：** DevMate AI Java 智能代码审查 Agent
**英文名：** DevMate AI — RAG-based Java Code Review Agent

一句话介绍：

> 导入 Java Git 项目后，以 Git Diff 确定审查范围，通过静态分析与 Hybrid RAG 补充调用链、配置和数据库上下文，再由受控 Tool Calling Agent 输出有真实位置、证据和验证方法的结构化审查结果。

该项目用于证明两类能力：

1. 使用 Spring Boot、MySQL、Flyway、JGit、AST 和 PMD 建设可靠审查任务系统的 Java 工程能力。
2. 使用 RAG、Embedding 和受控 Tool Calling 将大模型落地到私有代码上下文检索和可验证审查流程的 AI 应用能力。

当前求职版只围绕代码审查闭环继续开发。新项目生成模块保留但冻结，未来恢复时再完成真实模型分析、工程生成和编译测试。

## 2. 为什么不是普通 AI 聊天

直接调用大模型只能基于已有上下文生成文本，无法自动获得企业私有源码和实时业务数据，也不能安全执行外部操作。

DevMate AI 的边界是：

- 大模型负责理解自然语言、规划步骤和选择工具。
- Java 负责权限、参数校验、事务、工具执行和安全边界。
- RAG 负责检索与问题相关的私有代码和文档。
- 任何高风险或确定性操作都不交给模型自由执行。

可以概括为：**AI 负责理解与规划，Java 负责可靠执行。**

## 3. 核心用户场景

### 3.1 AI 代码审查（当前产品主线）

用户导入包含 Git 历史的 Java 仓库。系统固定审查 revision，通过 Diff、静态规则和 RAG 收集证据，再由 Agent 在只读工具白名单内完成取证和审查。

主流程固定为：`导入项目 → 解析源码 → 生成 Diff → 静态分析 → Hybrid RAG → Agent 取证 → 结构化报告 → 反馈与评测`。

第一版只生成审查建议，不自动修改、提交或合并代码。

### 3.2 从一句话生成新的 Spring Boot 项目（保留但冻结）

用户先用一句话描述业务目标。Agent 不立即盲目生成代码，而是输出需求和架构草案、显式假设与关键问题；用户确认后，系统调度受控 Tool 分阶段生成新的模块化 Spring Boot 项目，并实际执行编译、测试和代码审查。

主流程固定为：`一句话需求 → 草案与反向提问 → 用户确认 → 工程生成 → 编译测试 → 质量报告`。

第一版只生成新的 Spring Boot 模块化单体，不修改导入项目，不生成 Spring Cloud。详细范围见 [双模板产品与工程生成 Agent](PRODUCT_MODES_AND_GENERATION_AGENT.md)。

### 3.3 导入并深度理解项目（审查上下文能力）

用户提供 Java Git 仓库。系统完成源码导入、结构化解析和知识索引，并进入项目理解工作台：

- 汇总 Java 文件、包、类、方法、配置、数据库结构和调用关系
- 浏览真实文件、符号、注解、行号及跨文件引用
- 用自然语言检索业务入口、调用链、配置和数据访问证据
- 按 Controller → Service → 数据与配置 → 测试的顺序给出阅读起点
- 在形成代码证据后再辅助制定修改范围和开发方案

主流程固定为：`导入项目 → 一键解析 → 中文深层报告 → 搜索/阅读源码 → 基于证据问答 → 开始开发`。

### 3.4 AI 代码审查范围

用户提交 Git Diff 或指定提交版本。系统先执行确定性静态检查，再识别变更符号并通过 RAG 检索调用方、配置、数据库结构和相关规范，最终审查：

- 并发安全、竞态条件和锁粒度
- 事务边界与数据一致性
- Redis 缓存一致性、击穿与热点 Key
- RabbitMQ 消息丢失、重复消费和幂等性
- SQL 索引、循环查询和分页性能
- 越权、注入和敏感信息泄漏
- 模块职责、接口耦合和可维护性

输出必须包含文件位置、问题分类、严重程度、置信度、判断证据、触发场景、修改建议和验证方法。

### 3.5 代码理解

用户询问“登录流程在哪里实现”。系统检索相关代码，返回入口类、调用链和关键实现，并给出文件与符号来源。

### 3.6 Bug 诊断

用户提交异常堆栈或日志。Agent 定位异常位置，检索关联代码，区分事实、推断和待验证项，并给出排查步骤。

### 3.7 Git 变更影响分析

系统分析本次提交影响的模块、调用链、接口、缓存和数据结构，为代码审查提供上下文并生成建议测试范围。

### 3.8 企业技术规范问答

系统从架构文档、接口规范和编码规范中检索依据，避免模型凭空生成团队规则。

### 3.9 已有项目的需求分析（后续能力）

用户输入对已有项目的新需求。Agent 结合导入的项目结构和团队规范生成影响范围和修改计划；第一版不直接修改导入项目。

## 4. 第一版核心能力

### 新项目生成路线（保留但冻结）

- 一句话创建需求会话，Agent 输出结构化需求与架构草案
- 对影响角色、流程、数据和一致性的缺口主动反向提问
- 用户确认后固定方案版本并创建生成任务
- 在隔离工作区生成新的 Spring Boot 模块化单体
- 生成业务实现、Flyway、接口、配置、异常处理、测试和文档
- 通过白名单 Maven Tool 实际编译和测试
- 复用静态分析与代码审查输出质量报告和失败证据
- 当前尚未实现，不在 README“已具备”或简历经历中提前宣称

### 已有项目理解主线（底座已实现，深层报告待补）

- Git 项目导入与失败状态记录
- Java AST、配置与数据库迁移解析
- 文件、类、方法、注解、行号和引用关系浏览
- 本地 Embedding 与混合检索索引
- 面向业务问题返回带文件、符号和行号的代码线索
- 前端把 Diff、静态检查、模型审查和评测收纳到高级分析，不要求首次用户理解实现细节

### 高级混合代码审查流水线

- 接收 Git Diff，限定本次审查范围
- 输出完整、部分和跳过文件的覆盖清单，禁止静默漏审
- 通过 AST 将变更行映射到真实类、方法和证据锚点
- 使用静态检查工具发现确定性问题
- 解析变更类、方法及依赖关系
- 使用 RAG 补充完整方法、调用链、配置、SQL、测试和项目规范
- 使用大模型分析并发、事务、缓存和架构风险
- 合并、去重、校验证据与行号后输出结构化问题项
- 记录用户采纳、驳回和误报反馈

### Agent

- 分析用户目标
- 判断是否需要外部信息
- 选择一个或多个工具
- 汇总工具结果
- 输出带来源、风险和不确定性的答案

### RAG

- 解析 Java 源码和 Markdown 等文档
- 按类、方法和语义边界切片
- 生成 Embedding
- 按项目和版本进行向量检索
- 将高相关片段提供给大模型

### Tool

首批计划：

1. `analyzeGitDiff`：识别变更文件、符号和影响范围。
2. `runStaticAnalysis`：执行确定性静态检查并返回标准化结果。
3. `searchCode`：语义检索关联源码。
4. `searchKnowledge`：检索企业规范和技术文档。
5. `analyzeProjectStructure`：分析模块、包和依赖关系。
6. `analyzeStackTrace`：解析异常堆栈并定位符号。
7. `getIndexTaskStatus`：查询异步知识库构建状态。

详细流程和审查规则见 [代码审查 Agent 设计](CODE_REVIEW_DESIGN.md)。

## 5. 数据职责

### MySQL

保存结构化业务数据：

- 用户与权限
- 接入的项目
- 文档元数据
- 索引任务
- 会话与分析记录
- AI 调用指标

完整的表关系、字段职责和索引设计见 [数据库设计](DATABASE_DESIGN.md)。

### 向量存储

保存用于语义检索的代码和文档 Chunk。第一版先以易运行的方案验证 RAG，达到规模后再评估 Elasticsearch 或专用向量数据库。

### Redis（后续）

- 会话记忆
- 限流
- 短期缓存
- 分布式任务状态

### RabbitMQ（后续）

只处理耗时且无需同步等待的任务，例如代码仓库全量解析、批量 Embedding 和日志批处理。代码搜索、知识检索等即时交互继续使用同步调用。

## 6. 模块化单体结构

```text
com.devmate
├── common          通用响应、异常、基础配置
├── user            用户与权限
├── project         项目接入和管理
├── knowledge       文档/源码解析、切片、索引和检索
├── review          审查任务、问题项、反馈和评测
├── agent           Agent 编排、Prompt 和模型调用
├── tool            受控工具定义与执行
├── bug             故障分析记录
└── conversation    会话和 AI 调用记录
```

模块先通过 Java 接口协作，不跨模块直接操作对方的数据访问层。这样可以在保留单体开发效率的同时，为后续服务拆分建立边界。

## 7. 目标架构演进

第一阶段不使用 Spring Cloud。只有出现下列真实需求时才拆分：

- AI 调用耗时或并发与普通业务差异明显。
- 知识库构建需要独立扩容。
- 某个模块需要独立发布或故障隔离。

潜在拆分顺序：

1. `agent-service`
2. `knowledge-service`
3. `user/project-service`
4. Gateway、注册发现和服务治理

## 8. 安全与可靠性原则

- 模型不能直接连接数据库或执行任意 Shell。
- Tool 使用白名单能力、结构化参数和服务端权限校验。
- 检索必须按用户、项目和版本隔离。
- 所有模型调用设置超时、有限重试和降级提示。
- 答案区分“检索事实”和“模型推断”。
- 仓库源码、README 和注释均视为不可信数据，不能作为工具调用指令。
- 模型不得只根据被裁剪的 Diff 判断完整文件结构。
- API Key、密码和本地路径不进入 Git。
- 记录模型、Token、耗时、工具调用与失败原因，但不记录敏感源码全文。

## 9. 项目完成标准

项目不是以“调用过大模型”为完成标准，而是要形成可验证闭环：

1. 能导入真实 Java 项目并解析 Git Diff。
2. 能组合静态分析和 RAG 上下文。
3. 能发现至少一组并发、事务、缓存、MQ、SQL 和安全风险案例。
4. 每条审查结果都有代码位置、依据和验证方法。
5. 有固定评测集，记录命中、漏报和误报。
6. 能解释并现场修改核心实现。

同类项目的功能、架构和公开失败案例见 [同类开源项目对比与路线优化](OPEN_SOURCE_COMPARISON.md)。

## 10. 简历表达目标（完成功能后再使用）

> 基于 Spring Boot 与大模型构建 Java 代码审查 Agent，结合静态分析与 Git Diff 确定变更范围，通过 RAG 检索调用链、配置和项目规范，并使用 Tool Calling 调用代码搜索、项目结构分析等受控工具，输出包含位置、证据、风险场景和验证方法的结构化审查结果。

注意：只把已经实现并能现场解释、演示和测试的能力写进简历。
