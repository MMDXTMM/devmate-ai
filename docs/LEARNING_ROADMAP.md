# 面试导向学习与开发路线

## 1. 目标

本路线服务于 Java 后端校招/实习面试。目标不是尽快堆完所有框架，而是完成一个可运行、可演示、可测试并能独立讲解的 Java 智能代码审查 Agent。

建议按照 10 个里程碑推进。以每天 2–3 小时计算，可以按 10 周安排；实际进度以阶段验收为准，不为赶时间跳过理解和测试。

每个阶段结束时必须做到：

1. 能画出请求、数据和异常流转。
2. 能解释核心代码和技术取舍。
3. 能不依赖 AI 修改一个小需求。
4. 能通过日志或断点定位一次故障。
5. 有自动化测试或可重复验收步骤。

## 2. 每次学习与开发节奏

一次 2–3 小时的开发建议分为：

| 环节 | 建议时间 | 产出 |
|---|---:|---|
| 学习概念 | 30–40 分钟 | 能用自己的话解释原理 |
| 设计功能 | 20 分钟 | 输入、输出、约束、失败路径 |
| 编写代码 | 60–80 分钟 | 一个小而完整的功能 |
| 测试调试 | 30–40 分钟 | 正常、边界和异常用例 |
| 复盘记录 | 15 分钟 | 文档、Git 提交、面试问答 |

不要连续生成大量代码后再统一理解。每次只完成一个可以运行和验证的小闭环。

## 3. 里程碑路线

开发内容：

- 完成项目创建、详情、分页、修改和逻辑删除。
- 完成 DTO、参数校验、统一异常和状态管理。
- 使用 MyBatis-Plus 操作 MySQL。
- 增加接口、Service 和数据库测试。
- 增加 OpenAPI 接口文档。

必须掌握：

- HTTP 方法和常见状态码。
- Controller、Service、Mapper 的职责。
- IOC、依赖注入和 Spring Bean。
- AOP 代理和 `@Transactional` 事务边界。
- 主键、外键、索引、逻辑删除和分页。
- DTO 为什么不直接复用数据库实体。

AI 可以协助：

- 生成 DTO、字段映射和测试初稿。
- 检查参数边界和重复代码。
- 解释日志和 SQL。

开发者必须主导：

- `project` 表和接口契约。
- 事务范围、状态变化和异常语义。
- 测试场景及最终代码审查。

面试检查题：

- 一次创建项目请求经过哪些组件？
- `@Transactional` 在什么时候提交和回滚？
- 为什么删除项目使用逻辑删除？
- 为什么不能让客户端传入 `status` 和 `deleted`？

验收：能通过 API 完整管理项目，并在 MySQL 中验证结果。

AI 可以协助：

开发者必须主导：

### 里程碑 3：Git Diff、审查覆盖与精确定位（已完成）

开发内容：

- 读取两个 Git revision 之间的 Diff。
- 正确处理新增、修改、删除和 Rename。
- 把变更行映射到 Java 类、方法和注解。
- 生成完整审查、部分审查和跳过文件覆盖清单。
- 建立代码证据锚点，由服务端映射真实行号。

必须掌握：

- Git Diff、Hunk、base/head revision 和三点比较。
- 新增、删除、重命名文件的差异。
- 为什么模型不能自由生成行号。
- 为什么“没有发现问题”必须附带审查覆盖范围。

AI 可以协助：

- 生成 Diff 解析测试样例。
- 补充 Rename、空 Diff 和大 Diff 边界案例。

开发者必须主导：

- 审查范围、覆盖语义和行号可信边界。
- 确认每个变更文件都能解释其处理结果。

面试检查题：

- 为什么代码审查应该以 Diff 为入口？
- 大 PR 因 Token 被截断时为什么不能仍然返回“审查完成”？
- 如何防止删除文件和 Rename 导致解析异常？

验收：每个变更文件都有完整、部分或跳过状态，且真实行号由确定性代码映射。

实现复盘：

- JGit 的 `Edit` 同时提供基准版本 A 区间和目标版本 B 区间，不能只保存 B 区间，否则删除行永远无法定位。
- 目标版本符号复用导入阶段持久化的 `knowledge_chunk`；基准版本只为本次 Diff 从 Git Blob 读取并在内存解析，避免知识库无限复制历史源码。
- 映射证据带 `BASE/TARGET`，面试时要能解释删除行属于基准版本，而新增行属于目标版本。
- Rename 是相似度检测，不只是文件名变化；固定测试同时覆盖纯 Rename 和 Rename 后修改内容。

### 里程碑 4：静态分析与项目规则

开发内容：

- 接入至少一种 Java 静态分析能力。
- 将工具结果转换成统一 Finding。
- 按路径、注解和框架特征选择事务、缓存、MQ、SQL 等规则。
- 对结果进行去重、严重程度映射和位置验证。

必须掌握：

- 编译问题、静态规则问题和语义风险的区别。
- 为什么确定性问题不应该交给 LLM 猜。
- 规则优先级、项目规则和系统默认规则。

AI 可以协助：

- 接入工具和生成结果转换器初稿。
- 补充规则测试样例。

开发者必须主导：

- 规则取舍、严重程度、误报判断和证据标准。

验收：确定性缺陷能稳定返回文件、行号、规则和严重程度。

当前已经掌握的实现：

- PMD 通过 Java API 在应用内运行，规则集由 DevMate 固定管理，不调用目标项目的 Maven/Gradle。
- 分析任务采用“准备短事务 → 工具执行 → 完成/失败短事务”，避免耗时分析占用数据库事务。
- Finding 通过规则、路径、行号和消息生成指纹，数据库唯一键提供最终去重保护。
- 静态问题必须直接命中目标版本 Diff 行；调用链和项目上下文相关问题留给下一阶段规则与 RAG。
- JDK AST 已提取调用表达式、配置引用和数据访问入口；只有同类唯一目标才建立确定 `target_chunk_id`。
- “调用事实”和“真实动态目标”必须区分，无法唯一解析时保留空目标而不是猜测。
- `@Transactional` 自调用规则依赖唯一解析的同类目标；循环查询和锁内 IO 规则只给出风险场景与验证建议。
- PMD 放在限时虚拟线程，数据库上下文在请求线程读取，避免依赖另一个线程不可见的未提交事务。
- 已将 YAML/Properties 展平为脱敏配置 Chunk，并把 `@Value`/`@ConfigurationProperties` 关联到候选定义。
- 面试时必须说明 Spring Profile 和环境变量会影响最终值，静态关联只提供证据候选，不宣称运行时唯一值。
- 已从受控迁移 SQL 提取表、列、索引和约束，并将实体注解关联到表定义；迁移事实不等于线上最终 Schema。

面试自测题：

- 为什么选择 PMD 而不是第一版就用 SpotBugs？
- PMD 在应用线程内执行时如何限制时间、文件数量和路径？
- 为什么不直接启用全部 PMD 规则？
- 如果 PMD 返回了旧代码中的问题，为什么当前提交不应该展示它？
- 任务失败后数据库中应该保留什么状态，为什么不能整段流程放进一个事务？
- 为什么方法名和参数数量仍不足以可靠解析所有 Java 调用？
- 为什么 Mapper 命名只能作为数据访问线索，不能直接判定 N+1 或高并发缺陷？
- Spring 默认代理模式下，为什么同一个 Bean 内部调用可能绕过 `@Transactional`？
- 数据库调用为什么不应该放在 synchronized 锁的范围内？
- 为什么知识库不能保存配置密码、令牌和连接串原文？
- 为什么同一配置键可以解析出多个候选目标？
- 为什么索引定义存在仍不能证明某条查询一定走索引？
- 为什么代码审查系统不应该直接连接生产数据库读取结构？

### 里程碑 5：面向变更的 RAG 与检索评测

开发内容：

- 对类、方法和文档生成 Embedding。
- 实现项目、版本和符号过滤。
- 混合检索完整方法、调用链、配置、SQL 和测试。
- 实现去重、重排、Token 预算和裁剪记录。
- 建立固定问题、期望文件和期望方法评测集。

必须掌握：

- Embedding、余弦相似度、Top-K 和元数据过滤。
- Chunk 边界、上下文完整性和版本一致性。
- Recall@K、Precision@K 与 Token 预算。
- 为什么 Diff 限定范围但不能替代完整文件上下文。

AI 可以协助：

- 接入模型 SDK 和向量存储适配层。
- 生成评测脚本和候选问题。

开发者必须主导：

- Chunk 策略、正确答案标注和失败案例分析。

面试检查题：

- RAG 如何为一个变更方法找到必要上下文？
- 为什么只给模型 Diff Hunk 容易产生误报？
- 如何记录由于 Token 预算被裁剪的上下文？

验收：变更相关代码稳定出现在前 K 个结果中，并能量化检索表现和裁剪范围。

当前已经掌握的实现：

- 使用 `project_id + revision` 隔离候选、关系和种子，外部 Chunk ID 不能跨项目复用。
- 以 Diff 目标符号作为确定性种子，再通过 `code_reference` 扩展调用、配置和数据库关系。
- 用符号、路径、内容词和逆文档频率建立 `lexical-graph-v1` 可解释基线。
- 通过内容哈希去重，并明确记录 Top-K、Token 预算和重复内容造成的裁剪。
- 候选达到扫描上限时显式返回不完整标记，避免把局部结果包装成完整召回。
- 将固定问题、预期文件/符号和 K 持久化，运行结果绑定 revision 与检索配置版本。
- 使用 Recall@K、Precision@K、HitRate@K 和 MRR 衡量召回与排序；未索引预期项不伪装成算法失败。
- 当前 Token 数是近似估算，接入具体模型后必须使用对应 tokenizer。

下一步要掌握：

- Embedding 维度、归一化、余弦相似度与批量请求；
- 向量存储适配层、幂等 `vector_id` 和版本过滤；
- 关键词、向量、关系图三路结果的融合和重排；
- 用同一评测集分析中文语义、同义词和跨文件检索的增益与失败案例。

当前已经完成的向量实现：

- `EmbeddingProvider` 隔离本地测试算法与 DashScope 真实语义模型，密钥只从环境变量读取。
- 使用项目、revision、provider、模型、维度和内容哈希构造索引版本，避免旧代码向量污染新提交。
- 远端 Embedding 在事务外分批执行，结果以短事务保存；失败后重复执行会跳过成功批次。
- `LEXICAL/VECTOR/HYBRID` 共用同一预算与返回协议，Hybrid 使用 RRF 融合不同量纲的排序。
- 请求向量模式但索引不可用时显式返回 `LEXICAL_FALLBACK`，评测不会把降级结果伪装为 Hybrid。
- MySQL 当前只承担小规模线性向量检索，能够讲清楚从适配层演进到 ANN 向量库的触发条件。

新增面试自测题：

- 为什么本地哈希向量适合测试闭环，却不能证明语义召回能力？
- 为什么向量索引需要绑定 provider、模型和维度？
- RRF 为什么不直接相加关键词分数和余弦相似度？
- 为什么 Embedding HTTP 请求不能处于数据库事务中？
- 如何保证批量向量化失败后可以安全重试？
- 如何用同一评测集判断 Hybrid 是否真的优于 Lexical？

### 里程碑 6：AI 代码审查 MVP

开发内容：

- 根据 Diff 检索调用链、配置、数据库和团队规范。
- 设计并发、事务、缓存、MQ、SQL、安全和架构审查规则。
- 让模型输出结构化 Finding。
- 每条结果包含证据、触发场景、建议和验证方法。

必须掌握：

- Prompt 的角色、约束、上下文和输出结构。
- Structured Output 和普通文本生成的区别。
- 置信度、事实、推断和待验证项的区别。
- 并发、事务、缓存和消息一致性的 Java 基础。

AI 可以协助：

- 生成 Prompt 候选版本和结构化输出模型。
- 作为第二视角提出潜在风险。

开发者必须主导：

- 审查规则、证据标准、误报判断和最终采纳。
- 亲自构造包含已知隐性风险的示例代码。

面试检查题：

- 如何证明模型发现的问题不是幻觉？
- 为什么每个问题都必须给出代码依据和验证方法？
- 如何审查事务失效、缓存一致性或重复消费问题？

验收：能够稳定识别一组预先设计的隐性风险案例。

当前已经掌握的实现：

- AI 审查使用独立任务，不复用静态分析状态；二者失败语义、成本和重试方式不同。
- 流程采用“准备短事务 → RAG/模型事务外执行 → 完成或失败短事务”，避免网络等待占用数据库连接和锁。
- `AiReviewModel` 隔离模型实现，DashScope Provider 只负责协议、超时、JSON 解析和脱敏异常。
- Prompt 把仓库内容标记为不可信数据，限定 JSON Schema、风险类别和结论语义。
- 服务端验证模型引用的 Chunk，只从数据库证据映射项目、revision、文件和行号。
- Structured Output 只解决格式概率，不替代枚举、范围、归属、重复和业务语义校验。
- 数据库唯一键承担并发幂等最终保护；超时任务转为失败后才允许重试。
- 审计只保存 Token、耗时、模型、Prompt 版本和请求哈希，不复制私有源码。

新增面试自测题：

- 为什么模型返回合法 JSON 仍然可能是不可信数据？
- 如何防止模型引用另一个项目的 Chunk？
- 为什么 `updateById(entity)` 不能可靠地把 nullable 幂等键清空？
- 模型超时、应用进程崩溃和数据库写入失败分别会留下什么状态？
- 为什么同步 MVP 可以接受，但高流量批量审查最终需要异步任务？

### 里程碑 7：Agent 与 Tool Calling

开发内容：

- 提供 `analyzeGitDiff`、`runStaticAnalysis`、`searchCode` 等工具。
- 允许 Agent 在受控范围内选择工具。
- 增加权限、参数校验、超时、最大步数和调用日志。

必须掌握：

- Agent 与普通 LLM 调用的区别。
- Tool 描述、参数 Schema、执行器和结果回传。
- 为什么大模型不能直接访问数据库或执行任意 Shell。
- 如何防止循环调用和越权。

AI 可以协助：

- 生成 Tool 适配代码和 Prompt 初稿。
- 补充异常、超时和错误参数测试。

开发者必须主导：

- 工具权限、安全边界、调用上限和失败降级。

验收：能够从日志还原 Agent 为什么选择某个工具以及工具返回了什么。

当前已经掌握的实现：

- Function Calling 是“模型返回工具名和 JSON 参数 → Java 执行 → 以 `tool_call_id` 回填结果 → 再调用模型”，不是模型直接运行 Java。
- `AgentToolRegistry` 决定唯一可调用白名单；Schema 用于提示模型，Java 校验才是可信边界。
- `projectId/revision/taskId` 来自服务端固定上下文，模型无法跨项目或切换版本。
- 使用单工具超时、输出上限、总步数与重复签名计数阻止卡死、循环和额度失控。
- `tool_call_log` 只保存参数哈希、键名和结果摘要，既能审计又不复制私有源码。
- 最终结构化审查复用 Chunk 白名单校验；Agent 没有成功检索代码时失败关闭。
- 保留固定流水线作为对照，阶段 8 用同一缺陷集比较质量、Token 与延迟，而不是主观宣称 Agent 更好。

新增面试自测题：

- 模型返回了 Schema 合法参数，为什么 Java 仍要重新校验？
- 未知 Tool、工具超时、重复调用和无证据停止分别如何落库？
- 为什么读取已有 Diff/静态结果比让 Agent 自动重跑更适合第一版？
- 如果将来增加修改代码 Tool，还需要哪些授权、审批和回滚机制？

### 里程碑 8：审查反馈与效果评测（进行中）

开发内容：

- 保存 Finding 的采纳、驳回、误报、延期和备注。
- 建立已知缺陷、标准答案与无缺陷对照样本。
- 使用同一 Diff 比较固定流水线与 Agent 的命中、漏报、误报、Token 和耗时。
- 分析无法自动匹配的 Finding，并由人工复核失败原因。

必须掌握：

- `PUT` 幂等语义、唯一键和项目归属校验。
- 反馈状态与标准答案的区别，特别是为什么 `REJECTED` 不等于误报。
- Precision、Recall、漏报、误报和无缺陷样本的意义。
- 为什么模型、Prompt、检索配置和 revision 必须固定后才能比较。

AI 可以协助：

- 生成反馈 API、Vue 交互和评测计算代码初稿。
- 补充边界测试和候选缺陷样本。

开发者必须主导：

- 定义标准答案、审查 Finding 匹配结果并解释失败案例。
- 决定哪些反馈能进入指标，防止用主观操作状态冒充事实标签。

验收：反馈可以可靠保存和恢复，并能用同一缺陷集生成可复现的两种审查路径对比报告。

当前已经掌握的实现：

- V12 对 `finding_id` 建唯一键，`PUT` 首次创建、再次提交更新同一资源。
- 服务端同时校验项目、Finding 和归属，避免通过 ID 越权写入其他项目。
- 认证未完成前不接受客户端 `userId`，避免伪造操作人。
- 最近审查响应批量回填反馈，避免 Finding 列表产生 N+1 查询。
- Vue 保存反馈只更新当前 Finding，不重新运行模型，因此不产生额外 Token 消耗。

下一阶段再学习的内容：

- RabbitMQ、增量索引、任务租约、重试和死信属于阶段 9，只有同步任务的耗时或吞吐数据证明需要后再引入。

### 里程碑 9：认证、安全、可观测性与部署

开发内容：

- Spring Security、JWT、项目成员和权限隔离。
- Redis 限流和短期会话。
- 模型耗时、Token、工具成功率和错误指标。
- Docker、Nginx、MySQL 和环境变量部署。

必须掌握：

- 认证与授权的区别。
- JWT 的生成、校验、过期和风险。
- Redis 常见数据结构、过期和缓存问题。
- 超时、重试、熔断和降级边界。
- 密钥管理和敏感日志脱敏。

AI 可以协助：

- 生成配置、部署文件和监控面板初稿。
- 检查常见安全配置问题。

开发者必须主导：

- 权限模型、数据隔离、限流值和故障降级方案。

验收：无权限用户不能访问其他项目，模型异常不影响普通业务接口。

### 里程碑 10：简历、演示与模拟面试

开发内容：

- 准备一个固定 Java 项目和多类风险提交。
- 演示导入、检索、审查、反馈和增量更新。
- 整理架构图、测试结果、失败案例和技术取舍。
- 根据实际代码生成最终简历项目经历。

必须掌握：

- 三分钟介绍完整项目。
- 从 HTTP 请求讲到数据库、RAG、Agent 和审查结果。
- 解释最困难的问题、失败方案和改进过程。
- 能现场修改小需求或定位一次异常。

验收：简历每一条描述都有对应源码、测试、运行记录和面试答案。

## 5. AI 使用红线

以下工作不能只依赖 AI 给出结论：

- 数据库关系、事务边界和状态机。
- 权限、并发、缓存、MQ 一致性和安全方案。
- RAG Chunk 策略和评测结果。
- Agent 工具权限和错误处理。
- 测试验收、故障定位和简历表述。

AI 生成代码后，开发者至少要能完成：

1. 指出入口类和核心方法。
2. 解释一条正常路径和一条失败路径。
3. 修改一个字段或业务规则。
4. 写出或补充一个测试。
5. 根据日志定位数据库或接口错误。

做不到以上五项时，该功能暂时不能写进简历。
