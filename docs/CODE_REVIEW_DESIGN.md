# AI 代码审查 Agent 设计

## 1. 目标与边界

代码审查是 DevMate AI 的主线能力。目标不是替代编译器或生成一段泛化评价，而是：

> 结合确定性工具和项目上下文，发现 Java 代码变更中的隐性工程风险，并提供可以验证的判断依据。

第一版只提供审查建议，不自动修改代码、不自动提交 Git，也不执行未经允许的任意命令。

## 2. 为什么采用混合审查

### 确定性静态分析负责

- 编译和类型错误
- 明确的空指针与资源泄漏风险
- 编码规范和复杂度
- 已知不安全 API
- 可由规则稳定识别的问题

### 大模型语义分析负责

- 竞态条件、锁粒度和线程安全
- 事务传播、事务失效和跨资源一致性
- 缓存更新时序、击穿、雪崩和热点 Key
- 消息丢失、重复消费、乱序和幂等性
- SQL 索引、循环查询和高并发数据库压力
- 认证、越权、注入和敏感信息泄漏
- 模块职责、接口耦合和兼容性风险

静态工具的结论不能由模型重新猜测；模型应消费标准化工具结果，并补充需要上下文推理的问题。

## 3. 审查流水线

```text
指定项目和 Git Diff
        ↓
校验项目权限与版本
        ↓
解析变更文件、方法和行号
        ↓
运行静态分析工具
        ↓
RAG 检索调用方、被调用方、配置、SQL、规范和测试
        ↓
按风险类别调用 AI 审查
        ↓
合并、去重、校验引用
        ↓
生成结构化 Finding
        ↓
用户采纳 / 驳回 / 标记误报
```

## 4. 审查结果模型

每条 Finding 至少包含：

| 字段 | 含义 |
|---|---|
| `file_path` | 问题所在文件 |
| `start_line/end_line` | 问题代码范围 |
| `category` | 并发、事务、缓存、MQ、SQL、安全、架构等 |
| `severity` | `INFO/LOW/MEDIUM/HIGH/CRITICAL` |
| `confidence` | 模型对判断的置信程度 |
| `title` | 简短问题标题 |
| `evidence` | 关联代码和工具结果依据 |
| `risk_scenario` | 什么情况下会真正出问题 |
| `suggestion` | 修改方向，不强制直接生成补丁 |
| `verification` | 如何通过测试或压测验证 |
| `source` | `STATIC/LLM/HYBRID` |

结论必须区分：

- **事实：** 工具结果或源码中可以直接证明的信息。
- **推断：** 结合上下文得出的可能风险。
- **待验证：** 缺少运行数据、配置或业务约束，不能直接下结论。

## 5. 上下文检索策略

不能把整个项目塞给模型。每个变更方法只检索必要上下文：

1. 变更前后代码。
2. 直接调用方和被调用方。
3. 同一事务或锁相关代码。
4. Redis Key、Lua、MQ Producer/Consumer。
5. Mapper、SQL 和表结构。
6. 相关配置和团队规范。
7. 已有单元测试和集成测试。

每个片段必须保留项目、版本、文件、符号和行号元数据，便于引用校验。

## 6. Tool 设计

### `analyzeGitDiff`

输入项目、基准版本和目标版本；输出变更文件、方法、行号和变更类型。

### `runStaticAnalysis`

执行白名单内的静态检查，输出统一的问题结构。工具进程需要超时、资源限制和工作目录隔离。

### `searchCode`

按项目、版本、语言和符号范围检索源码，不允许跨项目返回内容。

### `searchKnowledge`

检索架构规范、缓存规范、安全要求和接口文档。

### `analyzeProjectStructure`

返回模块、包、依赖和调用关系，为架构审查提供确定性信息。

## 7. 减少误报

- 没有代码证据时降低置信度或不输出。
- 对重复问题按文件、行号、类别和规则合并。
- 明确区分“可能风险”和“确认缺陷”。
- 保存用户采纳、驳回和误报反馈。
- 对高风险问题要求提供触发场景和验证步骤。
- 固定模型、Prompt、检索配置和评测集后再比较效果。

## 8. 评测方案

建立一个包含已知风险的 Java 示例项目或提交集，至少覆盖：

- 非原子检查后执行
- 锁范围过大或锁对象错误
- `@Transactional` 自调用失效
- 缓存与数据库更新顺序错误
- MQ 消费缺少幂等
- 循环查询和索引缺失
- 越权访问和敏感日志

第一版记录：

- 已知问题总数
- 成功发现数量
- 漏报数量
- 误报数量
- 平均审查耗时
- 每次调用 Token 消耗

在评测集足够稳定前，不宣称具体准确率或性能指标。

## 9. 第一版不做

- 自动修改并提交代码
- 自动合并 Pull Request
- 执行任意 Shell 或任意 SQL
- 支持所有编程语言
- 宣称替代人工 Code Review
- 没有评测依据的“企业级准确率”
