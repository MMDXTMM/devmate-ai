# 代码审查反馈闭环

## 1. 目标

阶段 8 不继续堆叠 Agent 框架，而是先收集开发者对审查结论的真实判断。反馈用于建立后续固定缺陷评测集、分析误报来源，并指导静态规则、检索策略、Tool 描述和 Prompt 版本迭代。

当前反馈只表达“开发者如何处理这条 Finding”，不直接等价于标准答案：

- `ACCEPTED`：认可风险并准备采纳修改建议；
- `REJECTED`：当前不采纳，可能是风险容忍、上下文不适用或建议成本过高；
- `FALSE_POSITIVE`：明确判断为误报；
- `DEFERRED`：证据不足或暂时无法处理，留待后续验证。

因此，阶段 8 后续统计准确率时必须结合人工标注集，不能简单把所有 `REJECTED` 都算作误报。

## 2. 请求与状态变化

```text
PUT /api/projects/{projectId}/review-findings/{findingId}/feedback
        ↓
校验 projectId 和 findingId 为正数
        ↓
校验反馈枚举与 1000 字备注上限
        ↓
短事务：确认项目存在且 Finding 属于该项目
        ↓
按 finding_id 新增或更新唯一反馈
        ↓
最近 AI 审查响应内返回持久化反馈
```

同一 Finding 当前只保留一条最新反馈。数据库唯一键 `uk_code_review_feedback_finding` 是并发重复提交的最终保护；接口使用 `PUT` 表达可重复更新同一资源。

## 3. 数据库 V12

`code_review_feedback` 保存：

- `project_id`：显式项目隔离，也便于按项目统计；
- `finding_id`：关联静态或 AI Finding，并设置唯一键；
- `feedback_type`：四种稳定枚举；
- `comment`：可选、最多 1000 字的判断依据；
- `created_at/updated_at`：区分首次反馈和最近修改。

外键删除策略：项目或 Finding 被删除时反馈随之删除，避免孤立评测数据。

当前系统尚未完成登录鉴权，因此 V12 不接受客户端传入 `userId`，避免伪造操作人。阶段 10 接入 Spring Security 后再新增服务端认证得到的 `user_id`，并把唯一范围扩展为“Finding + 用户”。

## 4. API 契约

请求示例：

```json
{
  "feedbackType": "FALSE_POSITIVE",
  "comment": "调用方已经持有同一把互斥锁"
}
```

失败路径：

- 项目不存在：404；
- Finding 不存在或不属于当前项目：404，不暴露其他项目信息；
- 枚举值未知、JSON 无法解析：400；
- 反馈类型为空或备注超过 1000 字：400。

反馈请求不会重新运行 Diff、静态分析、RAG 或模型，不产生模型 Token 消耗。

## 5. 前端交互

每条 AI Finding 下方提供备注框和四个明确操作。保存成功后只替换当前 Finding 的反馈状态，不刷新或重跑整个审查任务；重新打开弹窗时由最近审查接口恢复反馈。

前端 ID 始终使用字符串，反馈类型使用 TypeScript 联合类型，不保存用户身份、模型 Key 或数据库凭证。

## 6. 验证与限制

- H2 从空库执行 V1–V12；
- 后端测试覆盖首次提交、更新同一反馈、跨项目拒绝、非法枚举和备注边界；
- 前端测试覆盖 API 契约、误报提交、局部状态更新和失败提示；
- 后端 96 项测试、前端 24 项测试和 Vue 生产构建通过；
- 本机 MySQL 已从 V11 成功迁移到 V12，健康检查为 `UP`，原项目数据保持可读。

当前只完成反馈采集，不包含准确率统计。下一小阶段将建立已知缺陷样本和评测运行表，用同一 Diff 比较固定流水线与 Agent。

## 7. 面试必须掌握

4. 为什么当前不允许客户端提交 userId？
5. H2 测试通过后为什么还需要真实 MySQL 迁移验证？
