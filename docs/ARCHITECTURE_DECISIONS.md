# 架构决策记录

## ADR-001：先模块化单体，后微服务

**状态：** 已接受

当前最重要的是验证项目管理、代码检索、RAG 和 Agent 的完整闭环。提前拆成多个网络服务会增加注册发现、配置、远程调用和分布式一致性成本，却没有带来已验证的收益。

模块之间仍应保持清晰边界，禁止跨模块直接依赖内部 Mapper，为未来拆分保留条件。

## ADR-002：Java 21 + Spring Boot 3.5

**状态：** 已接受

项目选择 Java 21 LTS。Spring Boot 3.5 仍支持 Java 21，并与当前 MyBatis-Plus 的 Boot 3 Starter 配合。暂不升级 Spring Boot 4，以降低学习期的第三方生态兼容成本。

## ADR-003：MyBatis-Plus

**状态：** 已接受

结构化业务数据需要明确的数据访问层。MyBatis-Plus 提供常用 CRUD 能力，同时保留自定义 SQL 的空间。不会把复杂业务查询硬塞进通用 CRUD。

## ADR-004：Flyway 管理数据库结构

**状态：** 已接受

Git 不适合保存数据库物理文件。通过版本化迁移脚本确保两台电脑、测试环境和未来云环境拥有一致结构。

## ADR-005：默认 local Profile 使用 MySQL，测试使用 H2

**状态：** 已接受

日常运行默认激活 `local` Profile 并连接本机 MySQL，确保前端看到的数据与 DataGrip 一致。所有自动化测试显式激活 `test` Profile，并使用 H2 内存数据库隔离测试数据，避免测试修改真实项目。涉及 MySQL 特性的查询仍需在 MySQL 环境补充验证。

## ADR-006：同步查询与异步任务分开

**状态：** 已接受

代码搜索和知识检索需要即时结果，使用同步调用。全量解析、批量 Embedding 和日志批处理耗时长，后续使用消息队列异步执行。不会为了“用了 MQ”而让全部 Tool 异步化。

## ADR-007：模型不能直接访问底层资源

**状态：** 已接受

模型只选择预定义 Tool。Java 服务对工具参数、权限、资源范围和超时负责。禁止模型直接访问数据库、执行任意 SQL 或 Shell。

## ADR-008：代码审查作为项目主线

**状态：** 已接受

项目从通用研发助手收敛为 Java 代码审查 Agent。代码问答和 Bug 诊断仍然保留，但主要用于支撑审查上下文和结果解释。核心闭环调整为 Git Diff、静态分析、RAG 上下文检索、LLM 语义审查、结构化问题和用户反馈。

## ADR-009：采用静态分析与 LLM 混合审查

**状态：** 已接受

编译、规则和已知模式等确定性问题由静态工具负责；并发、事务、缓存、MQ、性能和架构等上下文问题由大模型辅助分析。模型不得取代确定性工具，也不得在缺少证据时把推断表述为确认缺陷。

## ADR-010：第一版审查不自动修改代码

**状态：** 已接受

第一版只输出审查建议和验证方法，由开发者确认、驳回或标记误报。自动修改、提交和合并会引入更高的权限与供应链风险，在审查效果和安全边界没有得到评测前不实现。

## ADR-011：项目元数据更新采用字段白名单

**状态：** 已接受

项目修改接口只更新名称、描述、源码类型、源码位置、默认分支和更新时间，不对查询出的完整实体直接执行全字段更新。这样可以防止客户端修改系统字段，也减少后台索引任务并发更新 `status`、`current_revision` 时被旧实体覆盖的风险。若后续需要解决多个用户同时修改相同元数据的问题，再为 `project` 增加版本号并启用乐观锁。

## ADR-012：BIGINT ID 在 JSON 中使用字符串

**状态：** 已接受

数据库和 Java 内部继续使用 `BIGINT/Long`，项目响应中的 ID 使用字符串序列化。这样避免雪花 ID 超过 JavaScript 安全整数范围后发生精度丢失，同时不改变数据库索引和服务端计算方式。

## ADR-013：前端采用独立 Vue 工程

**状态：** 已接受

**决定：** 前端使用独立的 Vue 3 + TypeScript + Vite 工程，开发期通过 Vite 代理访问 Spring Boot `/api`。

**原因：** 项目后续会出现代码浏览、审查报告和 Agent 交互等复杂界面，独立工程更适合组件化、测试和独立部署。开发代理可以保持浏览器同源调用体验，生产环境再由 Nginx 统一转发。

## ADR-014：Git 导入使用 JGit 和短事务状态机

**状态：** 已接受

Java 服务使用 JGit 克隆指定分支并获取 revision，避免拼接和执行用户可控的 Shell 命令。克隆与文件扫描属于不可事务回滚的外部操作，不放入长数据库事务；系统通过 `RUNNING → SUCCEEDED/FAILED` 任务状态以及项目状态实现可追踪的最终一致。

第一版同步执行以保持流程易理解、易调试。等仓库规模和并发需求有真实数据后，再将同一业务流程放入 MQ 消费者，而不是提前增加消息一致性复杂度。

## ADR-015：审查采用 Diff-first，但上下文不能 Diff-only

**状态：** 已接受

Git Diff 用来确定本次必须覆盖的变更范围，并生成可审计的覆盖清单；语义判断时则按 AST 符号补充完整方法、必要的完整文件和直接依赖。这样既控制 Token，又避免模型把被裁剪的 Diff Hunk 误判为残缺代码。

LLM 不负责生成最终行号。模型引用 `symbolId/chunkId` 和证据片段，Java 服务结合当前 revision、AST 与 Diff 完成位置映射。第一版不采用多 Agent 投票，先用单模型、确定性校验和固定评测集测出真实瓶颈。

## ADR-016：私有仓库开发期使用进程级只读凭证

**状态：** 已接受

开发阶段通过环境变量向 JGit 注入用户名和 Token，不把凭证拼进仓库 URL，也不保存到数据库或日志。公开仓库在没有 Token 时继续匿名访问。

该方案只适合单用户开发和演示。多用户部署时，每个项目需要独立授权、撤销和轮换能力，因此将升级为 GitHub App Installation Token；不会把共享个人 PAT 作为生产架构。

## ADR-017：采用项目级轻量工程规范，不引入通用后台脚手架

**状态：** 已接受

当前阶段继续使用 Spring Boot 模块化单体，并通过根目录 `AGENTS.md`、`.editorconfig`、`CONTRIBUTING.md`、工程规范和运维手册约束开发。规范覆盖模块边界、事务、数据库迁移、日志、安全、测试、发布和故障恢复。

暂不引入与智能代码审查主线无关的通用后台脚手架。脚手架虽然能快速提供菜单、字典和代码生成等功能，但也会增加依赖、升级和安全维护成本，并掩盖项目真正需要掌握的业务闭环。后续只有在认证、审计、任务调度或监控形成真实需求时，才按能力引入成熟组件。

## ADR-018：第一版 Java 结构解析使用 JDK Compiler Tree API

**状态：** 已接受

第一版使用 JDK 自带的语法树 API 解析 package、类型、方法、注解和源码位置，不编译或执行目标仓库，也不要求目标项目依赖可解析。这能以较少依赖完成 Diff 行号映射所需的稳定语法结构。

当前不做完整的跨文件类型绑定。进入调用图和复杂语义分析阶段后，如果 JDK AST 无法满足符号解析需求，再基于实际缺口评估 JavaParser Symbol Solver、Eclipse JDT 或专用语言服务，而不是提前替换。

## ADR-019：Diff覆盖必须显式记录未映射内容

**状态：** 已接受

每次Diff任务持久化所有变更文件，并使用 `FULL/PARTIAL/SKIPPED` 表达映射程度。非Java文件、删除文件和缺少AST数据的文件不能被过滤后仍返回“审查成功”，必须携带跳过或部分映射原因。

第一版优先映射目标版本的新增和修改行。删除行需要读取基准版本AST，因此当前明确标记为部分覆盖，后续补齐双版本符号映射；在此之前不会把它包装为完整审查。
