# 分阶段开发路线

每个开发阶段对应的知识点、AI 协作边界和面试检查题见 [面试导向学习与开发路线](LEARNING_ROADMAP.md)。

## 总原则

每个阶段都必须满足：

1. 能运行，有明确输入和输出。
2. 有自动化测试或可重复验收步骤。
3. 能解释设计取舍，而不只是展示框架用法。
4. 不提前引入没有真实需求的复杂组件。
5. 简历只记录已经实现、测试并能独立讲解的能力。

- 已完成 `project → index_task → knowledge_document` 状态闭环和重复 revision 幂等写入。
- 已提供执行导入与查询最近任务接口，并接入 Vue 项目列表。

- 已通过 33 个后端测试、8 个前端测试、前端生产构建和真实 MySQL V3 迁移验证。
- 阶段 2 已完成；下一步进入 Git Diff、覆盖清单与精确位置映射。

## 阶段 3：Git Diff、覆盖清单与精确定位

目标：以可验证方式确定“改了什么、审了什么、哪里没有审”。

- 读取两个 revision 之间的 Diff
- 处理新增、修改、删除和重命名文件
- 将变更行映射到 Java 类和方法
- 生成完整/部分/跳过文件覆盖清单
- 按模块、依赖和文件特征生成审查单元
- 建立服务端行号和代码证据锚点

验收：每个变更文件都有明确处理结果，删除和 Rename 不崩溃，不能出现静默审查 0 文件。

当前进度：

- 已使用 JGit 比较指定提交，默认比较 `HEAD^ → HEAD`，克隆历史深度调整为 50。
- 已识别 `ADD/MODIFY/DELETE/RENAME/COPY`，记录新增、删除和目标版本变更行区间。
- 已建立 `code_review_task` 和 `code_review_file`，保存任务状态与完整覆盖清单。
- 已将目标版本 Java 变更行映射到 `knowledge_chunk` 类和方法符号。
- 已定义 `FULL/PARTIAL/SKIPPED`，非 Java 与删除文件不会静默丢失。
- 已提供创建与查询最近 Diff 报告接口，并接入 Vue 报告界面。
- 已分别保存基准版本删除行和目标版本新增行区间。
- 删除行通过 Git 对象读取基准版本源码并在内存中解析 AST，不重复写入知识库。
- 映射结果明确标记 `BASE/TARGET`，删除文件也可形成完整覆盖证据。
- 已覆盖完全重命名和“重命名同时修改内容”的相似度 Rename 用例。
- 阶段 3 已完成；下一步进入确定性静态分析与项目规则。

## 阶段 4：确定性静态分析与项目规则

目标：先用工程规则覆盖模型不该猜测的问题。

- 关联调用方、配置和数据库结构
- 接入至少一种 Java 静态分析工具
- 将不同工具结果转换为统一问题模型
- 对相同问题进行合并和去重
- 支持按路径、注解和框架特征匹配项目规则
- 验证 Finding 引用的 revision、符号和真实行号

验收：提交一个包含确定性缺陷的 Diff，系统能返回文件、行号、规则和严重程度。

当前进度：

- 已接入 PMD 7.26.0 Java API，不执行目标仓库构建脚本。
- 已建立 `static_analysis_task` 和统一 `review_finding` 数据模型。
- 使用固定小规则集覆盖资源关闭、空 catch、集合返回 null、直接打印堆栈和无效局部变量。
- 只分析目标版本变更 Java 文件，并将违规过滤到本次 Diff 行，避免把历史问题归因给当前提交。
- 已实现 30 秒超时、200 文件上限、工作区路径校验、失败状态和 SHA-256 指纹去重。
- 已提供执行与最近报告接口，并接入 Vue 静态问题界面。
- 已从 Java AST 提取方法调用、配置键/前缀和数据访问入口，持久化为 `code_reference`。
- 同类方法调用仅在方法名、参数数量和目标唯一时建立确定关联；其他调用保留为未解析证据。
- 已提供当前 revision 关系查询接口，并在 Vue 源码结构浏览器展示引用和目标。
- 已实现 `@Transactional` 同类自调用、循环内数据访问和同步锁内数据访问三条项目规则。
- 项目规则同样只归因于目标版本 Diff 行，并在证据不足时使用“可能风险/待验证”语义。
- 已安全解析 YAML/Properties，只持久化配置键、类型、位置和脱敏摘要。
- 已将 `@Value` 精确键和 `@ConfigurationProperties` 前缀关联到候选配置定义与文件路径。
- 已解析迁移 SQL 的表、列、索引、约束和部分 ALTER，并关联 `@TableName/@Table` 实体映射。
- 当前完成阶段 4A、4B、配置与数据库上下文第一版；下一步进入检索评测与 RAG。

## 阶段 5：面向变更的上下文检索与 RAG

目标：为变更方法补齐判断隐性风险必需的项目上下文。

- 按类、方法和文档章节进行语义切片

- 检索完整方法、调用方、被调用方、配置、SQL 和测试
- 关键词与向量混合检索、去重和重排
- 对每个审查单元设置 Token 预算并记录裁剪内容
- 构建固定检索评测集

验收：变更相关的正确代码稳定出现在前 K 个结果中，且能说明哪些上下文因预算被裁剪。

当前进度：

- 已完成 `lexical-graph-v1` 基线：符号/路径/内容关键词排序与调用关系扩展。
- 已实现项目、revision 和外部种子 Chunk 的严格归属校验。
- 已实现内容哈希去重、Top-K、Token 预算和逐项裁剪原因。
- 已提供通用检索与最近成功 Diff 上下文接口，并接入 Vue 证据界面。
- 已新增 V8 固定评测用例/运行记录，计算 Recall@K、Precision@K、HitRate@K 和 MRR。
- `lexical-graph-v1` 继续作为可解释对照基线，用同一评测集和向量模式比较，不能只凭主观 Demo 宣称提升。
- 已完成 `EmbeddingProvider` 抽象，默认本地确定性哈希 Provider 用于测试，并提供 DashScope 真实语义模型适配。
- 已新增 V9 向量与索引任务表，使用项目、revision、provider、模型和维度严格隔离索引版本。
- 已实现幂等向量 ID、分批短事务保存、失败续建和显式任务进度；远端请求不占用数据库长事务。
- 已实现 `LEXICAL/VECTOR/HYBRID` 三种模式，以 RRF 融合关键词、向量与关系图证据。
- 向量缺失或远端调用失败会明确降级为 `LEXICAL_FALLBACK`；评测拒绝把降级结果计作 Hybrid 成绩。
- 前端已提供向量化入口、检索模式选择、实际执行模式、扫描上限和降级原因展示。
- 第一版 MySQL 向量存储是小规模开发适配器，不宣称具备生产 ANN 能力；后续根据数据规模替换专业向量库。
- 阶段 5 工程闭环已完成；真实检索增益仍需在重新导入的真实项目上建立固定标注集后量化。

## 阶段 6：AI 代码审查 MVP（项目核心）

目标：发现静态规则难以覆盖的语义和工程风险。

- 定义并发、事务、缓存、MQ、SQL、安全和架构审查规则
- 根据 Diff 检索调用链和项目上下文
- 构造受 Token 预算约束的审查 Prompt
- 生成结构化审查结果
- 每条结果包含位置、分类、严重程度、置信度、证据、风险场景、建议和验证方法
- 无证据时拒绝给出确定性结论
- 人工确认后再采纳，不自动修改或提交代码

验收：对预设隐性风险案例给出有代码依据、可复现的审查结果。

当前进度：

- 已建立独立 `ai_review_task` 状态机，固定最新成功 Diff 和对应静态分析，不把模型失败混入确定性工具结果。
- 已实现 DashScope OpenAI 兼容模型 Provider、JSON 结构化输出、连接/读取超时和缺少密钥的可观察失败。
- Prompt 使用版本号和请求哈希审计，不保存完整私有源码、Prompt 或模型响应。
- 以 Diff 目标 Chunk 执行 Hybrid RAG；模型只能引用本次提供的 Chunk ID，真实文件和行号由 Java 映射。
- 已校验类别、严重程度、事实/推断/待验证、置信度、字段长度、重复项和最多 Finding 数。
- 使用数据库 `running_key` 唯一键防止同一 Diff 并发执行，并自动回收超时 RUNNING 任务。
- 已提供执行/最近结果接口和 Vue 报告弹窗；打开弹窗不会自动消耗模型额度。
- 后端 87 项测试、前端 18 项测试和生产构建通过；真实模型效果仍需 API Key 和阶段 8 固定缺陷集验证。
- 阶段 6 工程闭环已完成；下一步进入受控 Agent 与 Tool Calling。

- `searchKnowledge`

- 工具参数校验、权限检查和超时
- 最大调用步数和循环防护
- 工具调用审计和失败降级

验收：Agent 能根据问题选择必要工具，并可通过日志还原完整调用链。

当前进度：

- 已实现 Qwen Function Calling 多轮协议和独立 Agent 审查接口，同时保留固定流水线作为评测对照。
- 工具白名单为 `getDiffCoverage/getStaticAnalysis/searchCode/analyzeProjectStructure`；第一版全部只读，不隐式重跑任务。
- 项目、任务和 revision 由服务端固定；工具参数执行 JSON Schema 对应的 Java 二次校验。
- 已增加单工具超时、输出上限、最多 6 次调用、相同调用最多重复 2 次和未知工具失败审计。
- 至少一次代码检索成功并获得真实 Chunk 后才能进入最终审查；无证据时失败关闭。
- V11 和 Vue 可以按顺序还原脱敏调用链；后端 93 项、前端 21 项测试与生产构建通过。
- 阶段 7 工程闭环已完成；真实模型 Tool 选择质量与固定流水线优劣在阶段 8 用同一缺陷集量化。

## 阶段 8：审查反馈与评测

目标：证明项目效果，而不是只展示生成文本。

- 建立包含已知缺陷的评测项目或提交集
- 覆盖并发、事务、缓存、MQ、SQL 和安全类别
- 记录问题是否被用户采纳、驳回或标记为误报
- 统计命中、漏报、误报和审查耗时
- 保存模型、Prompt 版本和检索配置
- 根据反馈调整规则与 Prompt

验收：能够用评测数据解释系统擅长什么、容易误报什么。

当前进度：

- 已通过 V12 建立 `code_review_feedback`，使用 Finding 唯一键保存最新反馈。
- 已实现 `ACCEPTED/REJECTED/FALSE_POSITIVE/DEFERRED` 四种反馈和 1000 字可选备注。
- 反馈接口同时校验项目与 Finding 归属，跨项目请求统一返回不存在。
- 最近 AI 审查响应会带回反馈；Vue 可以局部保存和恢复反馈，不重新调用模型。
- 当前尚未认证，因此不采信客户端 userId；阶段 10 再绑定服务端认证身份。
- V13 已建立 `DEFECT/CLEAN` 固定用例、数据集版本和评测运行快照，并为 AI 任务保存 `FIXED/AGENT` 执行模式。
- 标准答案使用类别、相对文件和行区间；唯一一对一重叠自动匹配，歧义项进入人工复核且不混入自动指标。
- 已计算 TP、FP、FN、Precision、Recall、F1，并同时保存 Token、延迟和 Tool 调用成功率；相同 AI 任务和数据集哈希幂等返回。
- Vue 已支持绑定最近成功 Diff 录入标准答案、评测最近已保存 AI 任务，并排展示 FIXED/AGENT 的质量、Token、耗时和 Tool 成功率。
- 执行模式由后端任务固定，评测界面不会调用模型；部分匹配明确标记为不完整指标。
- 本轮全量验证已通过后端 120 项、前端 37 项、48 项 Node 验收/A-B 工具测试与生产构建；H2 已从空库执行 V1-V15，隔离 MySQL 26.7 已验证 V13→V14→V15，应用健康及历史项目/Diff 回读通过。
- 已建立 `known-defects-v1` 样本契约，以独立 base/candidate 快照覆盖并发、事务、缓存、消息、SQL、安全、性能和 CLEAN 对照，并自动校验路径、行号及真实变更范围。
- 已使用确定性 JGit 生成器将快照转换为 8 个 `case-NNN` 分支，每个分支为 base/candidate 两次提交，并固定 revision 映射。

- 已建立零第三方依赖的真实导入/Diff 验收工具，核对项目配置、任务状态、revision、唯一 Java `MODIFY`、双方变更行、覆盖计数和 candidate 符号证据。

- 隔离 MySQL 首次得到 `8 created / 8 verified`，立即重跑为 `0 created / 8 reused / 8 verified`；最终落库 7 条 `DEFECT`、1 条 `CLEAN`，分别绑定 8 个项目和 8 个 Diff。
- `PARTIAL` 文件只要缺陷行有 TARGET 证据仍可录入，覆盖缺口继续单独报告。
- FIXED/AGENT 创建请求已显式携带预期 Diff ID、revision 和 UUID v4 attemptKey；服务端先执行只读校验，再在创建审计与任务状态的短事务内重复校验，Diff 在两次校验间漂移时会在模型调用前失败且不留下 AI 审计状态。
- 已完成受控 A/B 执行器：完整运行先对 8 个项目、revision、Diff、静态分析和标准答案做零模型全批预检，再按项目执行 `FIXED → 评测 → AGENT → 评测`；任一预检漂移时零付费 POST，执行失败后停止全部后续场景。
- 已通过 Mock/Fake 覆盖预期 Diff 绑定、全批漂移拒绝、AI/评测响应丢失、并发同配置任务隔离、失败即停、微平均聚合和失败报告脱敏。付费 POST 不自动重试；V15 保存唯一 attemptKey，恢复只按该键读取并再次校验项目、Diff、revision、模式和模型。
- 下一步仅在显式确认运行环境已配置模型密钥且额度充足后执行 1 个真实 canary；canary 完整通过后才执行 8 组真实 FIXED/AGENT A/B。当前尚未产生真实指标，结果稳定前仍不宣称准确率或 Agent 优于固定流水线。

## 阶段 12：按真实需求拆分服务

只有在监控数据表明存在独立扩容或故障隔离需求时再拆分：

- Agent/Review：模型调用慢，需要独立限流和扩容。
- Knowledge：解析和索引资源消耗高。
- 普通 Web 业务：保持稳定、低延迟。

拆分时再引入 Gateway、注册发现、配置中心和远程调用，不把“使用微服务”本身当作目标。
