# 分阶段开发路线

## 当前小闭环：Spring AI 中文项目深度理解报告

- 当前账户选择的 DeepSeek、通义千问或 OpenAI 模型可以通过 Spring AI 生成中文项目理解报告。
- 模型输入固定为当前项目 revision、静态业务地图和受限代码证据；输出只能引用输入中真实存在的 Chunk ID。
- Java 服务端校验引用并回填文件、行号和代码块，模型伪造证据时任务失败，不把模型文本冒充源码事实。
- 报告使用 `attempt_key` 避免一次点击重复计费，`running_key` 阻止同项目同版本并发生成，超时任务会失败并释放重试入口。
- 页面打开时不会自动调用模型，只有用户明确点击“生成新的深度报告”才会产生额度消耗。
- 下一步由用户使用自己的模型 API Key 和已导入项目完成真实页面验收；通过前不宣称真实模型输出质量。

每个开发阶段对应的知识点、AI 协作边界和面试检查题见 [面试导向学习与开发路线](LEARNING_ROADMAP.md)。

当前唯一开发主线调整为“基于 RAG 的 Java 代码审查 Agent”。已有项目理解继续作为审查所需的代码上下文能力；一句话生成 Spring Boot 项目的现有代码和数据契约全部保留，但暂时冻结，不继续投入开发时间。

## 总原则

每个阶段都必须满足：

1. 能运行，有明确输入和输出。
2. 有自动化测试或可重复验收步骤。
3. 能解释设计取舍，而不只是展示框架用法。
4. 不提前引入没有真实需求的复杂组件。
5. 简历只记录已经实现、测试并能独立讲解的能力。

## 当前求职版收敛顺序

以下闭环优先于生成项目、异步化、部署和微服务扩展。每完成一个闭环都暂停，由用户在页面验收并完成一次口述复盘后才继续。

### R1：一键代码审查业务闭环（已完成，待用户页面验收）

- 以已导入的 Java 项目为输入，提供明确的“开始代码审查”主入口。
- Java 编排器按顺序检查或执行源码解析、Diff、静态分析、向量索引和 Agent 审查，失败即停并展示可读阶段和恢复动作。
- 默认使用 Agent 模式；FIXED 模式保留为评测对照，不让普通用户先理解内部流水线。
- 报告统一展示覆盖文件、确定性 Finding、AI Finding、工具调用证据和未审查范围。
- 模型未配置、429、Diff 不存在、索引失败和重复提交均形成可查询失败状态。

验收：用户导入一个包含至少两次提交的 Java 仓库后，可以从一个入口获得完整审查报告，不需要手工依次点击五个技术步骤。

当前进度：已完成 V22 编排运行表、五阶段 Java 编排、请求幂等、项目级并发控制、超时恢复、失败阶段和恢复动作，并接入 Vue 主入口及最近运行状态。Fake 模型端到端成功链路与失败/权限/重复/并发路径均有自动化测试；真实模型效果仍属于 R4 验收范围。

### R2：中文项目业务地图与深层理解

- 把源码解析结果定位为“证据层”，不再把类、方法和代码片段列表当成项目理解结果。
- 基于 Controller、Service、Mapper、Entity、迁移 SQL、配置和调用关系，生成项目目标、模块职责、业务角色、核心流程、状态变化和数据关系。
- 每条业务判断引用真实文件、符号和行号，并区分源码事实、系统推断和仍需用户确认的内容。
- 输出推荐阅读顺序、首个开发入口和关键代码块，帮助从未接触项目的开发者先理解业务，再进入具体源码。
- 项目业务地图同时作为后续代码审查的全局上下文，避免 Agent 只围绕局部 Diff 做孤立判断。

验收：用户导入一个陌生 Spring Boot 项目后，能够从一份中文报告讲清项目做什么、核心业务怎样流转、数据如何变化，以及应该先读哪些代码。

当前进度：已完成 R2 第三小闭环。系统先从 Spring Web Controller 与映射注解生成 `STATIC_CODE_EVIDENCE_V2` 业务地图，再由当前账户选择的模型通过 Spring AI 归纳项目目标、架构、核心业务流程、阅读顺序与未知项。每条模型流程必须引用白名单 Chunk，真实文件、行号和代码由 Java 服务端回填；报告固定 revision、provider、model 和 Prompt 版本，并记录 Token、耗时、幂等、失败与超时恢复状态。原静态导览、业务下钻和文件结构继续保留。真实厂商输出质量仍待用户使用自己的 API Key 页面验收，动态路由、反射和运行时行为也仍需人工确认。

### R3：RAG 审查证据与中文可解释报告

- 每条 AI Finding 展示真实代码块、文件、行号、关联符号和证据来源。
- 区分静态规则事实、模型推断和待验证项，避免把模型意见包装成确定事实。
- 展示为什么召回该上下文、是否降级为关键词检索、哪些内容因 Token 预算被裁剪。
- 提供中文风险场景、修改建议和可执行验证步骤，并允许采纳、驳回和标记误报。

验收：开发者能够从报告中的代码证据复现判断，并能解释 RAG 为什么比只发送 Diff 更适合发现跨文件风险。

### R4：真实模型 canary 与固定缺陷集评测

- 先对单个公开虚构用例运行真实模型 canary，成功后再决定是否执行完整 8 组 FIXED/AGENT 对照。
- 保存模型、Prompt、检索配置、Token、耗时和工具成功率，付费请求不自动重试。
- 使用人工标准答案计算 TP、FP、FN、Precision、Recall 和 F1；结果不稳定时如实记录局限，不为简历美化数据。

验收：至少有一条可复现的真实模型审查链路；只有完整评测完成后才能在简历中填写具体指标或比较 Agent 与固定流水线。

### R5：演示、文档与面试理解闭环

- 固定一个公开演示仓库和一条能体现跨文件上下文价值的 Diff。
- 整理 5 分钟演示路径、架构图、核心表、任务状态机和三项真实问题复盘。
- 用户必须能独立解释 Diff-first、Hybrid RAG、Tool 安全边界、事务边界、幂等与失败恢复。
- 简历只保留 4～5 条最有证据的职责，不继续堆叠未使用技术。

验收：不依赖 AI，用户能够完成项目介绍、核心链路讲解和至少一个故障排查故事。

## 保留但冻结：Spring Boot 工程生成路线

以下 G1-G4 保留为未来路线，不删除现有实现，但当前不优先于 R1-R5。完整设计见 [双模板产品与工程生成 Agent](PRODUCT_MODES_AND_GENERATION_AGENT.md)。

- 增加正常、反复修改、拒绝确认和模型失败测试

验收：没有接触过仓库的用户能根据报告找到启动入口、核心业务、数据库关系和首个开发位置。
