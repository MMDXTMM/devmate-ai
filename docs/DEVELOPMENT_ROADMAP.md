# 分阶段开发路线

每个开发阶段对应的知识点、AI 协作边界和面试检查题见 [面试导向学习与开发路线](LEARNING_ROADMAP.md)。

## 总原则

每个阶段都必须满足：

1. 能运行，有明确输入和输出。
2. 有自动化测试或可重复验收步骤。
3. 能解释设计取舍，而不只是展示框架用法。
4. 不提前引入没有真实需求的复杂组件。
5. 简历只记录已经实现、测试并能独立讲解的能力。

## 阶段 0：基础工程与数据库（已完成）

- Java 21、Spring Boot 3.5、Maven Wrapper
- 统一响应、异常处理和健康检查
- MyBatis-Plus、Flyway、H2/MySQL 双环境
- 用户、项目、知识库、会话和 AI 审计第一版表结构
- MySQL 真实迁移验证

验收：项目可以连接 MySQL 启动，V1、V2 迁移成功。

- Controller、Service、Mapper 分层
- 统一错误码
- 审计时间和状态流转
- OpenAPI 文档
- Service 与接口测试

验收：可以通过 API 管理一个待审查的 Java 项目。

## 阶段 2：源码导入与结构化解析

目标：安全读取真实 Java 项目并建立文件与符号元数据。

- 本地目录、压缩包或 Git 仓库导入接口抽象
- 路径穿越、文件数量和文件大小限制
- Java 文件白名单与忽略规则
- 解析包、类、方法、注解和行号
- 计算路径哈希和内容哈希
- 写入 `knowledge_document`、`knowledge_chunk`
- 使用 `index_task` 记录任务进度

验收：导入示例项目后，可查询文件、类、方法和源码位置。

## 阶段 3：代码知识库与第一版 RAG

目标：根据问题或代码变更检索关联源码。

- 按类、方法和文档章节进行语义切片
- Embedding 与向量存储接口抽象
- 项目、分支和提交版本隔离
- Top-K 与元数据过滤
- 关键词和向量混合检索
- 上下文去重与 Token 预算
- 构建固定检索评测集

验收：预设问题的相关代码稳定出现在前 K 个结果中。

## 阶段 4：Git Diff 与静态分析

目标：得到可靠的变更范围和确定性检查结果。

- 读取指定提交或两次提交之间的 Diff
- 识别新增、修改和删除的文件与方法
- 关联调用方、配置和数据库结构
- 接入至少一种 Java 静态分析工具
- 将不同工具结果转换为统一问题模型
- 对相同问题进行合并和去重

验收：提交一个包含确定性缺陷的 Diff，系统能返回文件、行号、规则和严重程度。

## 阶段 5：AI 代码审查 MVP（项目核心）

目标：发现静态规则难以覆盖的语义和工程风险。

- 定义并发、事务、缓存、MQ、SQL、安全和架构审查规则
- 根据 Diff 检索调用链和项目上下文
- 构造受 Token 预算约束的审查 Prompt
- 生成结构化审查结果
- 每条结果包含位置、分类、严重程度、置信度、证据、风险场景、建议和验证方法
- 无证据时拒绝给出确定性结论
- 人工确认后再采纳，不自动修改或提交代码

验收：对预设隐性风险案例给出有代码依据、可复现的审查结果。

## 阶段 6：Agent 与 Tool Calling

目标：让模型在受控边界内选择完成审查所需的工具。

- `analyzeGitDiff`
- `runStaticAnalysis`
- `searchCode`
- `searchKnowledge`
- `analyzeProjectStructure`
- 工具参数校验、权限检查和超时
- 最大调用步数和循环防护
- 工具调用审计和失败降级

验收：Agent 能根据问题选择必要工具，并可通过日志还原完整调用链。

## 阶段 7：审查反馈与评测

目标：证明项目效果，而不是只展示生成文本。

- 建立包含已知缺陷的评测项目或提交集
- 覆盖并发、事务、缓存、MQ、SQL 和安全类别
- 记录问题是否被用户采纳、驳回或标记为误报
- 统计命中、漏报、误报和审查耗时
- 保存模型、Prompt 版本和检索配置
- 根据反馈调整规则与 Prompt

验收：能够用评测数据解释系统擅长什么、容易误报什么。

## 阶段 8：增量索引与异步任务

- 根据 Git Diff 和内容哈希只更新变更文件
- 删除失效 Chunk 和向量记录
- RabbitMQ 异步执行索引与批量审查
- 幂等键、失败重试和死信处理
- 任务进度和失败恢复

验收：修改单个文件不会触发全项目重新 Embedding。

## 阶段 9：认证、权限与可观测性

- Spring Security + JWT
- 用户、项目成员和角色
- 项目级检索与审查数据隔离
- Redis 限流和短期会话
- AI Token、延迟、工具成功率和错误指标
- Prompt 注入防护与敏感数据脱敏

验收：无权限用户无法审查其他项目，模型异常不会拖垮普通业务接口。

## 阶段 10：部署、演示与面试准备

- Docker 镜像与测试环境 MySQL
- Nginx、环境变量和密钥管理
- 数据库自动迁移与备份
- 演示项目和固定审查场景
- 架构图、压测记录和面试问题
- 逐条核对简历描述是否有代码和测试证据

## 阶段 11：按真实需求拆分服务

只有在监控数据表明存在独立扩容或故障隔离需求时再拆分：

- Agent/Review：模型调用慢，需要独立限流和扩容。
- Knowledge：解析和索引资源消耗高。
- 普通 Web 业务：保持稳定、低延迟。

拆分时再引入 Gateway、注册发现、配置中心和远程调用，不把“使用微服务”本身当作目标。
