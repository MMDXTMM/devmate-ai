# 分阶段开发路线

每个开发阶段对应的知识点、AI 协作边界和面试检查题见 [面试导向学习与开发路线](LEARNING_ROADMAP.md)。

## 总原则

每个阶段都必须满足：

1. 能运行，有明确输入和输出。
2. 有自动化测试或可重复验收步骤。
3. 能解释设计取舍，而不只是展示框架用法。
4. 不提前引入没有真实需求的复杂组件。
5. 简历只记录已经实现、测试并能独立讲解的能力。

## 阶段 0：基础工程与数据库（已完成）

- Java 21、Spring Boot 3.5、Maven Wrapper
- 统一响应、异常处理和健康检查
- MyBatis-Plus、Flyway、H2/MySQL 双环境
- 用户、项目、知识库、会话和 AI 审计第一版表结构
- MySQL 真实迁移验证

验收：项目可以连接 MySQL 启动，V1、V2 迁移成功。

## 阶段 1：项目管理业务闭环（已完成）

- 项目新增、详情、分页、修改和逻辑删除
- DTO 参数校验
- Controller、Service、Mapper 分层
- 统一错误码
- 审计时间和状态流转
- OpenAPI 文档
- Service 与接口测试

验收：可以通过 API 管理一个待审查的 Java 项目。

当前进度：

- 已完成 `POST /api/projects` 创建项目接口。
- 已完成 `GET /api/projects/{id}` 项目详情接口。
- 已完成名称校验和 Git 仓库地址业务校验。
- 已完成创建、详情、异常响应和数据库写入测试。
- 已使用真实 MySQL 验证创建与详情查询闭环。
- 已完成分页、名称/状态筛选和项目元数据修改。
- 更新接口使用字段白名单，避免覆盖状态和索引版本。
- 已完成逻辑删除，并验证删除后详情、分页不可见以及重复删除返回 404。
- 项目雪花 ID 在 JSON 中按字符串返回，避免前端发生大整数精度丢失。
- 已通过 17 个自动化测试完成项目管理基础 CRUD 回归。
- 已完成独立 Vue 3 + TypeScript 项目管理前端，覆盖筛选、新增、修改和删除。
- 已通过 Vite 代理完成前后端真实 CRUD 联调，并通过 6 个前端测试、生产构建和依赖安全审计。
- OpenAPI 文档作为后续接口治理任务补充，不阻塞源码导入主线。

## 阶段 2：源码导入与结构化解析

目标：安全读取真实 Java 项目并建立文件与符号元数据。

- 本地目录、压缩包或 Git 仓库导入接口抽象
- 路径穿越、文件数量和文件大小限制
- Java 文件白名单与忽略规则
- 解析包、类、方法、注解和行号
- 计算路径哈希和内容哈希
- 写入 `knowledge_document`、`knowledge_chunk`
- 使用 `index_task` 记录任务进度

验收：导入示例项目后，可查询文件、类、方法和源码位置。

当前进度：

- 已完成 HTTPS Git 地址校验、指定分支浅克隆和提交 revision 获取。
- 已完成 Java 文件白名单、忽略目录、符号链接防护，以及数量和容量限制。
- 已完成 `project → index_task → knowledge_document` 状态闭环和重复 revision 幂等写入。
- 已提供执行导入与查询最近任务接口，并接入 Vue 项目列表。
- 已使用 JDK AST 解析 package、类、嵌套类、构造器、方法、注解和准确起止行。
- 已将符号内容、哈希和元数据写入 `knowledge_chunk`，重复 revision 会替换同一文档的 Chunk。
- 已提供源码文件与符号查询接口，并在 Vue 中提供源码结构浏览器。
- 已通过 33 个后端测试、8 个前端测试、前端生产构建和真实 MySQL V3 迁移验证。
- 阶段 2 已完成；下一步进入 Git Diff、覆盖清单与精确位置映射。

## 阶段 3：Git Diff、覆盖清单与精确定位

目标：以可验证方式确定“改了什么、审了什么、哪里没有审”。

- 读取两个 revision 之间的 Diff
- 处理新增、修改、删除和重命名文件
- 将变更行映射到 Java 类和方法
- 生成完整/部分/跳过文件覆盖清单
- 按模块、依赖和文件特征生成审查单元
- 建立服务端行号和代码证据锚点

验收：每个变更文件都有明确处理结果，删除和 Rename 不崩溃，不能出现静默审查 0 文件。

当前进度：

- 已使用 JGit 比较指定提交，默认比较 `HEAD^ → HEAD`，克隆历史深度调整为 50。
- 已识别 `ADD/MODIFY/DELETE/RENAME/COPY`，记录新增、删除和目标版本变更行区间。
- 已建立 `code_review_task` 和 `code_review_file`，保存任务状态与完整覆盖清单。
- 已将目标版本 Java 变更行映射到 `knowledge_chunk` 类和方法符号。
- 已定义 `FULL/PARTIAL/SKIPPED`，非 Java 与删除文件不会静默丢失。
- 已提供创建与查询最近 Diff 报告接口，并接入 Vue 报告界面。
- 已分别保存基准版本删除行和目标版本新增行区间。
- 删除行通过 Git 对象读取基准版本源码并在内存中解析 AST，不重复写入知识库。
- 映射结果明确标记 `BASE/TARGET`，删除文件也可形成完整覆盖证据。
- 已覆盖完全重命名和“重命名同时修改内容”的相似度 Rename 用例。
- 阶段 3 已完成；下一步进入确定性静态分析与项目规则。

## 阶段 4：确定性静态分析与项目规则

目标：先用工程规则覆盖模型不该猜测的问题。

- 关联调用方、配置和数据库结构
- 接入至少一种 Java 静态分析工具
- 将不同工具结果转换为统一问题模型
- 对相同问题进行合并和去重
- 支持按路径、注解和框架特征匹配项目规则
- 验证 Finding 引用的 revision、符号和真实行号

验收：提交一个包含确定性缺陷的 Diff，系统能返回文件、行号、规则和严重程度。

## 阶段 5：面向变更的上下文检索与 RAG

目标：为变更方法补齐判断隐性风险必需的项目上下文。

- 按类、方法和文档章节进行语义切片
- Embedding 与向量存储接口抽象
- 项目、分支和提交版本隔离
- 检索完整方法、调用方、被调用方、配置、SQL 和测试
- 关键词与向量混合检索、去重和重排
- 对每个审查单元设置 Token 预算并记录裁剪内容
- 构建固定检索评测集

验收：变更相关的正确代码稳定出现在前 K 个结果中，且能说明哪些上下文因预算被裁剪。

## 阶段 6：AI 代码审查 MVP（项目核心）

目标：发现静态规则难以覆盖的语义和工程风险。

- 定义并发、事务、缓存、MQ、SQL、安全和架构审查规则
- 根据 Diff 检索调用链和项目上下文
- 构造受 Token 预算约束的审查 Prompt
- 生成结构化审查结果
- 每条结果包含位置、分类、严重程度、置信度、证据、风险场景、建议和验证方法
- 无证据时拒绝给出确定性结论
- 人工确认后再采纳，不自动修改或提交代码

验收：对预设隐性风险案例给出有代码依据、可复现的审查结果。

## 阶段 7：Agent 与 Tool Calling

目标：让模型在受控边界内选择完成审查所需的工具。

- `analyzeGitDiff`
- `runStaticAnalysis`
- `searchCode`
- `searchKnowledge`
- `analyzeProjectStructure`
- 工具参数校验、权限检查和超时
- 最大调用步数和循环防护
- 工具调用审计和失败降级

验收：Agent 能根据问题选择必要工具，并可通过日志还原完整调用链。

## 阶段 8：审查反馈与评测

目标：证明项目效果，而不是只展示生成文本。

- 建立包含已知缺陷的评测项目或提交集
- 覆盖并发、事务、缓存、MQ、SQL 和安全类别
- 记录问题是否被用户采纳、驳回或标记为误报
- 统计命中、漏报、误报和审查耗时
- 保存模型、Prompt 版本和检索配置
- 根据反馈调整规则与 Prompt

验收：能够用评测数据解释系统擅长什么、容易误报什么。

## 阶段 9：增量索引与异步任务

- 根据 Git Diff 和内容哈希只更新变更文件
- 删除失效 Chunk 和向量记录
- RabbitMQ 异步执行索引与批量审查
- 幂等键、失败重试和死信处理
- 任务进度和失败恢复

验收：修改单个文件不会触发全项目重新 Embedding。

## 阶段 10：认证、权限与可观测性

- Spring Security + JWT
- 用户、项目成员和角色
- 项目级检索与审查数据隔离
- Redis 限流和短期会话
- AI Token、延迟、工具成功率和错误指标
- Prompt 注入防护与敏感数据脱敏

验收：无权限用户无法审查其他项目，模型异常不会拖垮普通业务接口。

## 阶段 11：部署、演示与面试准备

- Docker 镜像与测试环境 MySQL
- Nginx、环境变量和密钥管理
- 数据库自动迁移与备份
- 演示项目和固定审查场景
- 架构图、压测记录和面试问题
- 逐条核对简历描述是否有代码和测试证据

## 阶段 12：按真实需求拆分服务

只有在监控数据表明存在独立扩容或故障隔离需求时再拆分：

- Agent/Review：模型调用慢，需要独立限流和扩容。
- Knowledge：解析和索引资源消耗高。
- 普通 Web 业务：保持稳定、低延迟。

拆分时再引入 Gateway、注册发现、配置中心和远程调用，不把“使用微服务”本身当作目标。
