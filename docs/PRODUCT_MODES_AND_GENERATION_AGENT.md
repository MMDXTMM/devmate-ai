# 双模板产品与 Spring Boot 工程生成 Agent

> 当前优先级说明（2026-08-07）：求职版开发已切换为“基于 RAG 的 Java 代码审查 Agent”。本文件和现有 `generation` 模块全部保留，但工程生成路线暂时冻结；恢复开发前不继续接入真实需求模型或代码生成 Tool。

## 1. 产品定位

本文件记录曾规划的双模板完整产品形态；它不是当前求职版的开发优先级。两个模板彼此独立并共享底层工程能力：

1. **新项目生成模板**：用户用一句话描述目标，Agent 先形成需求和架构草案，主动追问关键缺口，经用户确认后生成完整、可运行、可测试的 Spring Boot 项目。
2. **已有项目理解模板**：用户导入陌生 Java Git 项目，系统解析代码、配置、数据库和调用关系，生成中文项目报告，并基于真实代码证据回答问题，帮助用户快速接手开发。

工程生成第一版原计划只支持全新的 Spring Boot 模块化单体，不修改导入项目，不生成 Spring Cloud 微服务。当前求职版已经把代码审查调整为产品主入口，双模板扩展需等审查闭环完成后再评估。

## 2. 为什么“一句话”不是“一次性生成”

一句话是低门槛入口，不代表跳过需求分析。直接根据模糊描述生成整个仓库，通常会把模型的猜测固化为错误的数据模型和接口。

第一版交互固定为：

```text
用户一句话描述
  → Agent 提取目标、用户、核心业务和约束
  → 生成需求草案、架构草案和显式假设
  → 针对影响数据模型或业务流程的缺口主动追问
  → 用户修改或确认方案
  → Agent 生成工程计划
  → 受控 Tool 分阶段生成项目
  → 编译、测试、规范检查和代码审查
  → 交付工程与生成报告
```

Agent 只追问会实质改变结果的问题，例如用户角色、核心状态流转、关键数据、外部系统和并发/一致性要求。命名、目录等低风险细节由默认规范补全，并在假设清单中展示。

### 2.1 Agent 先给专业判断，再让用户做业务选择

Agent 不能把专业设计工作转嫁给没有开发经验的用户。每轮交互先说明“我对需求的理解”和“我建议的方案”，再根据影响程度决定是否追问：

- **业务选择**：用户最清楚，应使用通俗语言追问，并尽量提供 2～4 个互斥选项。
- **技术决策**：Agent 默认给出推荐方案、理由和代价，用户可以直接选择“采用推荐方案”，不要求用户解释事务、幂等、索引或并发控制。
- **高影响取舍**：同时展示推荐项和备选项，例如“后台审核后生效（推荐）/自动生效/暂不确定”，说明每项会如何改变业务。
- **低风险细节**：Agent 按 Java 工程规范自行决定，并放入可修改的假设清单。
- **用户不确定**：每个专业问题都允许选择“我不确定，由 Agent 按行业常见方案决定”。

每个待确认项至少包含：问题类型、Agent 建议、建议理由、可选项、选项影响、是否允许自由补充。Agent 不能只抛出“预计并发量是多少”这类需要专业估算的问题；应改为可理解的使用规模选项，并由 Agent 映射到具体工程方案。

示例：

```text
Agent 判断：维修工单适合采用“待受理 → 处理中 → 待验收 → 已完成/已关闭”的状态机。

请选择验收方式：
A. 报修人确认后完成（推荐）——责任清晰，适合企业内部工单
B. 维修人员处理后直接完成——流程更短，但缺少验收
C. 超时自动完成——需要额外的定时任务和提醒机制
D. 我不确定，采用推荐方案
```

## 3. 新项目生成模板

### 3.1 输入

最小输入是一句业务目标，例如：

> 做一个面向大学生的实验室预约系统，老师可以审批，学生不能重复预约同一时段。

可选输入包括技术限制、数据库类型、认证方式、外部接口、预计数据量和特殊质量要求。

### 3.2 需求与架构确认

Agent 在写代码前输出结构化草案：

- 产品目标与不做事项
- 使用者和角色权限
- 核心用例与主流程
- 业务状态及合法转换
- 核心实体、关系和唯一性约束
- REST API 草案
- 模块边界和依赖方向
- 事务、一致性、并发和幂等要求
- 安全、审计和失败恢复要求
- 测试范围与验收场景
- 模型补全的假设和待确认问题

只有用户确认后才能进入代码生成，避免对错误方案进行大规模生成。

### 3.3 第一版交付物

生成结果不是页面样例或空壳 Controller，而是一个独立的新工程目录，至少包含：

- Java 21、Spring Boot 3.x、Maven Wrapper
- 按业务模块组织的模块化单体结构
- Entity、DTO、Controller、Service、Mapper 分层
- MySQL 表结构和只增不改的 Flyway 迁移
- 统一响应、参数校验和全局异常处理
- 基础登录认证与角色/资源访问边界（需求需要时）
- 明确的事务边界、唯一键和幂等约束
- 正常、边界和失败路径测试
- `application` 环境模板和敏感信息隔离
- README、业务流程、数据库和 API 说明
- Maven 编译与测试报告、未完成项和风险清单

第一版不承诺生成前端、不生成微服务、不自动部署，也不直接修改或提交用户已有仓库。

### 3.4 任务状态

```text
DRAFT
  → CLARIFYING
  → SPEC_READY
  → CONFIRMED
  → GENERATING
  → VERIFYING
  → READY / FAILED
```

- 需求与架构版本必须固定后再生成。
- 生成失败要保存失败阶段和可读原因，支持从安全检查点继续。
- 用户修改已确认方案时产生新版本，不能静默覆盖原方案。
- 模型调用、文件生成、Maven 验证不放在数据库长事务中。

## 4. 工程生成 Agent

### 4.1 职责划分

```text
LLM Agent
  负责需求理解、主动提出专业方案、生成用户可理解的选项、架构取舍、任务规划和结果总结

Java Orchestrator
  负责状态机、权限、预算、参数校验、执行顺序和失败恢复

受控 Tools
  负责确定性的文件生成、结构检查、编译测试和质量报告
```

工程思维主要存在于版本化的 System Prompt、架构规则、工程规范和验收策略中。Tool 不是一段“工程思维提示词”，而是参数明确、结果可验证的受控能力。

需求澄清第一版使用 `guided-requirement-v2` 稳定交互契约：问题分为业务问题、工程规则和重要取舍，输入支持单选、多选及自由文本。选择题必须给出 2～4 个带业务/代码影响的选项和明确推荐项；“采用推荐”与“由 AI 决定”会落到相同实际方案，但分别保存用户确认和 AI 代选来源。该 Provider 是规则实现，真实 LLM 接入后仍必须输出并通过 Java 校验同一契约。

### 4.2 第一批 Tool

1. `draftRequirementSpec`：把自然语言整理为结构化需求草案。
2. `validateArchitecturePlan`：检查模块边界、依赖方向、状态机和数据一致性设计。
3. `createSpringBootSkeleton`：从批准的模板创建基础工程。
4. `writeProjectFile`：只允许在本次生成工作区内写入白名单类型文件。
5. `inspectGeneratedProject`：读取生成目录结构、接口、迁移和测试覆盖清单。
6. `runMavenVerification`：执行白名单 Maven 编译和测试命令，限制时间与资源。
7. `reviewGeneratedCode`：复用静态分析、项目规则和证据约束审查能力。
8. `repairVerificationFailure`：根据编译或测试证据生成受限修复计划，再由写文件 Tool 执行。

Tool 不能执行任意 Shell、任意 SQL、访问任意目录或自行选择高风险依赖。

## 5. 已有项目理解模板

该模板不负责新项目生成，目标是让没有接触过仓库的人快速形成工程认知：

```text
导入 Git 项目
  → 解析模块、包、类、方法、配置、迁移和调用关系
  → 识别启动入口、分层边界、核心业务和数据流
  → 生成中文项目总览与推荐阅读顺序
  → 用户自然语言提问
  → RAG 检索真实代码证据
  → 输出中文解释、代码块、文件、符号和行号
  → 给出继续开发的入口和影响范围
```

深层解析报告至少包括：

- 项目用途和技术栈证据
- 模块/包职责与依赖方向
- 启动入口和请求处理链路
- 核心业务流程与状态变化
- Entity、表、迁移和数据访问关系
- 配置项及其代码使用位置
- 外部系统和框架集成点
- 测试结构、运行方式和关键命令
- 代码热点、未知项与推荐阅读顺序

报告中的事实必须引用代码证据；无法从仓库确认的内容标记为推断或待确认。

## 6. 两个模板共享的能力

- 用户、项目和任务权限
- 模型 Provider 适配与调用审计
- Prompt 和工程规范版本管理
- Java AST、配置与数据库迁移解析
- 关键词、向量与关系图混合检索
- 受控 Tool Calling 与参数校验
- 静态分析、工程规则和代码审查
- 编译、测试、失败记录和可恢复状态机

共享底座不代表共享业务入口。前端首页应先让用户选择“生成新项目”或“理解已有项目”，随后进入各自的工作台。

## 7. 第一版范围与验收

第一版的业务范围已确认聚焦**管理与业务流程型 Java 后端**，例如工单、预约、库存、内容管理和商城后台。此类项目具有明确的角色、数据模型、状态变化和业务规则，适合通过固定工程规范验证生成质量。游戏、实时音视频、复杂支付结算及其他强领域基础设施暂不纳入第一版承诺。

第一版工程生成满足以下条件才算完成：

1. 用户可用一句话创建生成会话。
2. Agent 能输出需求/架构草案，并对关键缺口至少完成一轮追问。
3. 用户确认的方案被版本化保存，生成任务绑定确定版本。
4. 系统在隔离目录生成一个新的 Spring Boot 模块化单体。
5. 生成工程包含数据库迁移、接口、业务实现、异常处理、配置和测试，不是空壳。
6. 系统实际运行 Maven 编译和测试，并保存结果。
7. 失败时返回具体阶段和证据；成功时提供运行说明、假设和风险清单。
8. 固定样例集可以重复生成并验证结构完整性，不用一次成功 Demo 代替评测。

已有项目理解模板的第一版验收继续以“真实仓库导入成功、中文深层报告、代码证据问答和可读代码块”为准。

## 8. 后续演进

- 第二阶段：允许 Agent 基于 Diff 受控修改已导入项目，并要求用户确认修改计划。
- 第三阶段：增加可选前端工程模板和前后端契约联动。
- 第四阶段：在存在独立部署、扩容和治理需求时增加 Spring Cloud 模板。
- 所有阶段都先用固定生成样例、编译测试和人工评审证明质量，再扩展技术范围。
