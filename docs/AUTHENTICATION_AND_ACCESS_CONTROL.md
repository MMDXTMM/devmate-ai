# 认证与项目访问控制

## 1. 目标与边界

阶段 10 第一小步为现有代码审查闭环增加可靠身份和项目隔离：

```text
注册/登录
  → BCrypt 保存密码哈希
  → 服务端签发有期限 JWT
  → Vue 在 sessionStorage 保存会话
  → 每个 API 请求携带 Bearer Token
  → 路径过滤器检查项目成员
  → Service 再检查业务角色
  → 项目数据、导入、检索和审查保持同一权限边界
```

当前实现不包含 Refresh Token、Redis Token 黑名单、管理员角色、成员邀请和密码找回。退出登录只清理浏览器会话；已签发 JWT 在到期前无法被服务端单独撤销。这些是明确边界，不应在简历中描述为已完成。

## 2. API

- `POST /api/auth/register`：注册并返回访问 Token。
- `POST /api/auth/login`：校验用户名和密码并返回访问 Token。
- `GET /api/auth/me`：返回当前认证用户。

公开接口只有注册、登录和健康检查，其余接口默认要求认证。JWT 只保存用户 ID、用户名、签发和过期时间，不保存密码，也不把项目权限写入 Token；项目成员关系始终以数据库当前状态为准。

## 3. 项目权限

创建项目使用一个数据库事务同时完成：

1. 写入 `project.owner_id`。
2. 写入 `project_member(project_id, user_id, OWNER)`。

任一步失败都会回滚，避免出现“项目存在但没有所有者”的半完成状态。项目列表通过成员关系过滤；详情和所有 `/api/projects/{projectId}/...` 子接口要求调用者至少是成员；项目元数据修改和删除要求 `OWNER`。

权限采用双层校验：

- `ProjectAuthorizationFilter` 覆盖导入、结构、Diff、静态分析、检索、AI 审查、反馈和评测等所有项目路径，防止新增 Controller 时遗漏权限。
- `ProjectServiceImpl` 在核心写操作再次校验角色，保护绕过 HTTP 入口的内部调用。

无成员关系统一返回 403，不通过 404 暴露项目是否存在。历史 `owner_id IS NULL` 项目不会自动公开给任意新用户；需要后续显式认领或迁移。

## 4. 前端会话

Vue 登录和注册页面直接调用认证 API。访问 Token 只存放在 `sessionStorage`，关闭标签页后自动消失；公共 API 客户端统一添加 `Authorization: Bearer ...`。后端返回 401 时客户端清理会话并回到登录页。

`sessionStorage` 仍可能被同源 XSS 读取，因此服务端仍需输出编码、输入校验和严格依赖治理。当前选择是减少长期持久化风险，不代表彻底解决 XSS。

## 5. 配置

安全在本地和生产环境默认启用，启动时要求：

```text
DEVMATE_JWT_SECRET：至少 32 个字符
DEVMATE_ACCESS_TOKEN_TTL：默认 8h
```

测试 Profile 默认关闭安全，保持原有确定性链路快速回归；专用安全集成测试显式开启安全并使用测试密钥。

## 6. 实际问题与解决方法

### Spring 多构造器导致 Bean 启动失败

`JwtService` 为可测试时钟增加第二个构造器后，Spring 无法判断注入入口，报错为没有默认构造器。修复方式是在生产构造器上明确标记注入入口。经验是构造器注入并不等于任意增加构造器；多个候选时必须明确容器应使用哪一个。

### 前端测试环境不等于真实浏览器

Node/jsdom 运行时没有可用的 `localStorage`，测试对其直接断言导致失败。实现本身只依赖 `sessionStorage`，因此测试改为验证实际存储目标，不为满足测试引入无关 polyfill。经验是测试应验证业务契约，而不是假设所有浏览器 API 在测试运行器中都存在。

### 路径过滤与业务角色不是同一层责任

只在项目 CRUD 检查权限会遗漏导入、RAG 和 Agent 等子模块；只用统一 Filter 又无法表达“成员可读、OWNER 才能删除”。最终使用路径层成员门禁与 Service 层角色规则组合，覆盖面和业务语义分别清晰。
