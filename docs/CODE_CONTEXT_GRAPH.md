# 代码上下文关系图

## 1. 目标

阶段 4B 需要判断事务失效、循环数据库访问和配置影响等项目级风险。仅保存类和方法源码还不够，系统必须先建立可验证的代码关系事实。

当前版本在源码导入时提取：

- `METHOD_CALL`：方法调用名称、限定对象、参数数量和真实行号；
- `DATA_ACCESS`：按 `Mapper/Repository/Dao/JdbcTemplate/EntityManager` 命名约定识别的数据访问入口；
- `CONFIG_KEY`：`@Value("${...}")` 引用的配置键；
- `CONFIG_PREFIX`：`@ConfigurationProperties` 使用的配置前缀。

这些记录是审查上下文，不等同于缺陷。项目级规则或后续 LLM 必须结合变更范围和其他证据才能输出 Finding。当前已基于它们实现事务自调用、循环数据访问和锁内数据访问三条首批规则。

## 2. 导入闭环

```text
Java 源码
  → JDK AST 解析类和方法
  → 在所属符号内提取调用/配置/数据访问引用
  → 保存所有 knowledge_chunk
  → 用“同一类型 + 方法名 + 参数数量”解析唯一目标
  → Java 精确配置键/前缀关联到脱敏配置 Chunk
  → 保存 code_reference
  → API/前端展示证据
```

引用必须在所有 Chunk 保存后统一解析，否则被调用方法尚未入库时会错误地标记为不存在。重复导入同一 revision 时先清理旧引用再重建，避免重复数据和失效 Chunk ID。

## 3. 为什么只解析确定目标

第一版没有完整执行 Java 类型归属分析，不能可靠解析跨类调用、继承方法和同参数数量的重载。因此只有下面条件同时满足才写入 `target_chunk_id`：

1. 调用未限定、使用 `this`，或使用当前类名限定；
2. 被调用方法属于同一个类型；
3. 方法名和参数数量匹配；
4. 候选目标唯一。

无法满足时仍保留调用事实，但 `target_chunk_id` 为空。宁可显示“未解析”，也不把猜测伪装成确定调用链。

## 4. 数据库与接口

`code_reference` 通过 `source_chunk_id` 关联调用来源，通过可空的 `target_chunk_id` 关联确定目标；删除源码 Chunk 时由外键清理或解除关联。

查询当前项目版本的关系：

```http
GET /api/projects/{projectId}/sources/references
```

前端源码结构浏览器会在每个类或方法下展示引用类型、位置和已解析目标。旧项目需要重新执行一次源码导入，才能生成 V7 引用数据。

配置引用允许一对多：同一键可能在多个 Profile 或 YAML 文档中定义。接口同时返回目标符号和目标文件路径，前端不把候选定义错误地展示成唯一运行时值。详细安全边界见 [配置上下文解析与关联](CONFIGURATION_CONTEXT.md)。

## 5. 面试需要掌握

- AST 提取“调用表达式”和类型分析得到“真实调用目标”不是一回事。
- 为什么同名重载不能仅靠方法名匹配。
- 为什么关系图在 Chunk 全部持久化后统一构建。
- 为什么数据访问命名识别只能作为上下文事实，而不能直接判定性能缺陷。
- 为什么 `target_chunk_id` 允许为空，以及这如何降低误报。
- 为什么配置引用可能有多个目标，以及静态分析为什么无法确定 Spring 最终生效值。
