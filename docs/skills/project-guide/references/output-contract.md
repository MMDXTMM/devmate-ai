# 输出约定（project-guide-v1）

## 对话或 Markdown

默认只给“做什么、给谁用、主要模块、事情如何发生”和必要未知项，再列可继续了解的模块。第二、三层在用户明确选择或要求完整报告时才展开。

保存 Markdown 时可在末尾折叠附上实现证据与覆盖范围；界面不支持折叠时只给简短范围说明和深入入口，收到追问再提供证据细节。操作日志属于验收记录，不放进默认产品内容。

流程必须同时说清步骤和关键判断。例子：“用户提交购买请求 → 检查资格与库存 → 符合条件才创建订单 → 返回结果”。这只是表达示例，不是每个项目都具有的业务。

不把“扫描了若干文件”写成“完整理解了项目”。能力较多时呈现主模块及其余模块入口，并说明哪些尚未深入。

## 接入产品时的结构化约定

这是目标契约设计。2026-11-11 已实现的首个产品契约将模型部分放入 guide.content，宿主负责 guide.snapshot/coverage/evidence；精确字段与尚未实现范围见 [产品接入记录](../../../PROJECT_GUIDE_IMPLEMENTATION.md)。宿主应先提供 JSON Schema/DTO，再请求结构化输出；不能让模型自定义前端期待的字段。

| 对象 | 内容与约束 |
|---|---|
| `schemaVersion` | 固定 `project-guide-v1`，旧报告按自身版本读取 |
| `snapshot` | 宿主提供的版本、工作树摘要/内容摘要、读取范围；不能仅以 HEAD 区分有未提交修改的快照；模型不得生成摘要冒充宿主快照 |
| `project` | 名称、类型、一句话用途、使用者、输入、输出、主场景、证据引用与结论状态；读不到时允许未知 |
| `modules[]` | 稳定字符串 ID、中文名称、职责、用户任务/能力、输入输出、关联模块 ID、实现状态、证据引用 |
| `flows[]` | ID、名称、目标、参与者、触发条件、模块 ID、步骤、规则、分支/失败结果、整体结果、未确认项 |
| `flows[].steps[]` | 中文动作、输入与结果、参与模块 ID、证据引用、结论状态；跨外部系统的不可见步骤要标记边界 |
| `flows[].rules[] / outcomes[]` | 可核对的条件与对应结果，证据引用和结论状态；不是无证据的字符串清单 |
| `glossary[]` | 实际使用的必要术语及一句通俗解释，无术语可为空 |
| `openQuestions[]` | 缺口、冲突或推断；影响哪项结论及还需什么证据 |
| `coverage` | 已侦察根目录、实际读取文件/证据范围、跳过/不可读范围、预算/抽样与能力限制；不可伪造完整覆盖率 |
| `evidence[]` | 宿主生成的证据 ID、相对路径、可选符号/标题、实际行区间、来源类型、快照；模型只引用，真实路径和代码由宿主回填 |

结论状态建议为 `observed / inferred / unknown`；来源类型区分 `implementation / documentation / test / configuration / runtime`。
`observed + implementation` 只表示源码观察；只有宿主确实提供执行记录才能使用 `runtime`。实现状态另用 `implemented / partial / planned / unclear`，不得与运行验证混为一谈。

主要模块、用途、步骤和规则都必须挂接证据或明确标为未知/推断；不要只给整条流程一份泛化证据，然后把其中无证据的业务规则当作事实。

### 宿主校验职责

1. 验证 JSON 结构、版本、枚举、数量与长度上限。
2. 证据 ID 必须属于当前用户、当前项目和当前快照的实际读取集合；符号、行号和片段由宿主生成/核对，不接受模型自报。
3. 模块及流程的交叉引用有效，流程关键规则的证据可定位；没有证据的事实改为未知或拒收，不能用占位 ID 填充。
4. 证据真实存在不等于支持结论；抽样人工核对语义，再考虑有预算的第二轮模型检查，避免自评等于真值。
5. 报告中不保存真实凭据、完整私有源码或敏感 Prompt。代码按授权和长度上限从证据存储回填。
6. 显示加载、空数据、部分完成和失败；未配置模型时可显示已确认的目录/类型信息，不能伪造业务总结。

优先让结构化内容能渲染为相同的三层导览，不另做一份内容可能冲突的“简版报告”。
