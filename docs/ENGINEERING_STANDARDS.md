# DevMate AI 工程开发与运维规范

## 1. 目标

本规范用于保证 DevMate AI 在持续增加源码解析、Diff、RAG 和 Agent 能力后仍然可理解、可测试、可排障和可部署。规范优先解决真实风险，不为展示技术而增加框架。

优先级从高到低：

1. 安全和数据正确性。
2. 可验证的业务行为。
3. 清晰的模块边界。
4. 可观测和可恢复。
5. 一致的代码风格。

## 2. 模块边界

```text
common          通用响应、错误、配置和基础设施约定
project         项目元数据和项目生命周期
knowledge       源码获取、解析、切片、索引和检索
review          Diff、审查任务、Finding、反馈和评测
agent           Prompt、模型调用和任务编排
tool            受控工具契约和执行边界
user            认证、用户和项目权限
conversation    会话与消息
bug             Bug 分析记录
```

规则：

- Controller → Service → Mapper 单向依赖。
- Controller 不包含业务状态判断，不直接访问 Mapper。
- 模块之间通过公开 Service/接口协作，不导入其他模块的内部 Mapper。
- `common` 只放跨模块稳定基础能力，不放具体业务 Service、Entity 或“万能工具类”。
- 外部系统通过接口适配，例如 `GitSourceClient`，业务层不依赖具体 SDK 实现。
- 只有出现独立扩容、发布或故障隔离需求时才拆微服务。

## 3. Java 命名与结构

- 包名全小写：`com.devmate.<module>.<layer>`。
- 类名使用明确职责后缀：`Controller`、`Service`、`Mapper`、`Request`、`Response`、`Properties`、`Client`。
- 请求对象使用 `CreateXxxRequest`、`UpdateXxxRequest`，响应使用 `XxxResponse`。
- 数据库实体放在 `entity`，不得直接作为 Controller 请求或响应。
- 状态和有限值使用枚举，数据库保存稳定的枚举名称；修改名称前需要迁移方案。
- 布尔变量使用 `enabled/available/deleted` 等可读名称，不使用含义不清的 `flag`。
- 方法名表达业务动作，例如 `prepareImport`、`completeImport`，避免 `handle/process/doSomething`。
- 依赖统一使用构造器注入，禁止 `@Autowired` 字段注入。
- 优先小方法和不可变 DTO；不要用继承构建复杂业务层次。
- 不使用 `@Data` 暴露 Entity 的全部字段；避免客户端或日志无意访问敏感字段。

格式由根目录 `.editorconfig` 统一：Java 四空格，YAML/TypeScript/Vue 两空格，UTF-8、LF、文件末尾换行。

## 4. API 规范

- REST 路径使用复数资源，例如 `/api/projects/{projectId}/imports`。
- `GET` 查询、`POST` 创建或触发任务、`PUT` 完整更新允许字段、`DELETE` 删除。
- 请求必须使用 Bean Validation，业务约束在 Service 再校验。
- 所有响应使用 `ApiResponse<T>`，异常交给全局异常处理器。
- HTTP 状态与业务错误一致：参数 400、未认证 401、无权限 403、不存在 404、冲突 409、内部错误 500。
- 错误消息对用户可读，但不返回堆栈、SQL、文件绝对路径、Token 或第三方原始响应。
- 数据库 `BIGINT/Long` ID 在 JSON 中以字符串返回，防止 JavaScript 精度丢失。
- 分页必须限制最大 `size`，列表接口必须有稳定排序。
- 对重复提交明确选择：拒绝、幂等返回或创建新版本，不能依赖偶然行为。

## 5. Service、事务与状态机

- Service 负责业务规则、权限、状态变化和跨组件编排。
- `@Transactional` 只包围需要原子提交的数据库操作。
- Git 克隆、文件 IO、HTTP、模型和 MQ 调用不得放入长数据库事务。
- 外部操作采用“准备短事务 → 外部执行 → 完成/失败短事务”，并保存可恢复任务状态。
- 状态转换必须明确，例如 `CREATED → INDEXING → READY/FAILED`。
- 并发入口使用数据库条件更新、唯一键或幂等键，不能只在 Java 内存中判断。
- `catch` 不得吞异常；转换异常时保留内部 cause，但外部只返回脱敏信息。
- 事务方法避免同类自调用导致 Spring 代理失效；需要独立事务边界时拆到单独 Bean。

## 6. 数据库规范

- 数据库结构只通过 Flyway 迁移，已经执行的迁移脚本不可修改。
- 表和字段使用小写蛇形命名；时间使用 `created_at/updated_at/finished_at`。
- 业务主表包含必要的状态、审计时间和逻辑删除字段。
- 外键是否使用数据库约束按删除策略决定，但代码和文档必须明确关系。
- 高频查询、外键和幂等条件需要索引；联合索引顺序必须对应查询条件。
- 唯一键承担最终幂等保护，不能只“先查再插”。
- 大文本、源码和向量不默认塞进业务表；MySQL 保存元数据、关系和存储引用。
- 禁止在生产启动时自动插入测试数据。
- H2 测试用于快速回归，涉及 MySQL 方言、锁或索引的功能必须补真实 MySQL 验收。

## 7. 日志与可观测性

日志至少能关联：

- `requestId`
- `projectId`
- `taskId/reviewId`
- 操作类型、状态、耗时和错误类别

规则：

- `INFO` 记录生命周期和关键结果；`WARN` 记录可恢复异常；`ERROR` 记录需要处理的失败。
- 禁止记录密码、Token、Cookie、Authorization、数据库连接密码和完整私有源码。
- 模型日志默认只保存模型名、Token 数、耗时、结果状态和 Prompt 版本，不保存完整 Prompt/响应。
- 不在循环中输出大量 INFO 日志。
- 异常只能在负责处理或最终边界记录一次，避免同一堆栈重复打印。
- 健康检查区分应用存活与依赖就绪；对外只暴露必要 Actuator 端点。

## 8. 外部调用与安全

- Git、LLM、Embedding、GitHub API 和静态工具都必须有超时。
- 重试只用于临时错误，并限制次数、退避时间；权限错误和参数错误不得无限重试。
- 仓库源码、README、注释和文档均是不可信数据，不能覆盖 System Prompt 或触发工具。
- 不执行仓库提供的任意脚本。静态工具只能从白名单启动，并限制工作目录、时间、CPU/内存和网络。
- 文件操作必须规范化路径、限制根目录、拒绝符号链接逃逸，并设置文件数和容量上限。
- 私有 Git 凭证只从环境或秘密管理系统读取，不进入 URL、数据库和日志。
- 模型只能选择预定义 Tool；Java 负责权限、参数和执行，禁止模型直接执行任意 SQL/Shell。

## 9. AI 与代码审查规范

- Diff 决定审查范围，但不能作为唯一上下文。
- 每次审查输出完整、部分和跳过文件覆盖清单。
- 模型引用 `symbolId/chunkId` 和证据；真实行号由 Java 根据 revision、AST 和 Diff 映射。
- Finding 区分事实、推断和待验证项，并包含风险场景和验证方法。
- 确定性问题优先由静态规则处理；模型不代替编译器和静态工具。
- Prompt、模型、检索配置和规则都需要版本号，保证评测可复现。
- 没有固定评测集前不宣称准确率；没有证据时不输出高置信度缺陷。
- 第一版不自动修改、提交或合并代码。

## 10. 前端规范

- TypeScript 类型与后端契约保持一致，ID 一律使用 `string`。
- API 调用集中在 `services`，页面组件不重复解析统一响应和错误。
- 组件区分加载、空数据、成功和失败状态。
- 危险操作需要确认，提交期间禁用重复操作。
- 不在前端保存 Git Token、模型 Key 或数据库凭证。
- 前端显示的状态必须来源于后端，不用本地假状态掩盖失败。

## 11. 测试标准

每个业务闭环至少覆盖：

1. 正常成功。
2. 参数边界。
3. 资源不存在或权限失败。
4. 外部依赖失败。
5. 重复提交或并发条件。
6. 数据库最终状态。

测试规则：

- 测试固定使用 `test` Profile，不污染本机 MySQL。
- 外部 Git/LLM 默认使用 Fake 或 Mock，真实集成另行记录验收结果。
- 修复 Bug 时先增加可以复现问题的测试。
- 不只断言 HTTP 200；必须检查响应业务码、关键字段和数据库状态。
- 后端提交前运行 `./mvnw test`；前端运行 `npm test -- --run` 和 `npm run build`。

## 12. 配置、发布与运维

环境分层：

- `test`：H2 和 Mock，不访问真实外部资源。
- `local`：开发者本机 MySQL 和显式环境变量。
- `prod`：独立数据库、秘密管理、只读/最小权限账号和结构化日志。

发布规则：

- 配置与代码分离；密钥只通过环境或秘密管理系统注入。
- 应用启动前校验数据库迁移，失败时停止发布。
- 保留健康检查和优雅停机，后台任务必须能标记中断或恢复。
- 数据库变更先备份并验证恢复流程；破坏性迁移采用分阶段兼容方案。
- 发布产物可追踪到 Git revision，日志记录应用版本但不记录密钥。
- 出现故障优先降级 AI/审查任务，不能拖垮项目管理等普通接口。

具体启动、检查和故障处理见 [运维手册](OPERATIONS_RUNBOOK.md)。

## 13. Git 和审查规范

- `main` 保持可构建；功能从独立分支开发。
- Commit 聚焦一个逻辑变化，消息说明意图而不只是文件名。
- 禁止提交 `target/`、`workspace/`、日志、IDE 文件、密钥和本地配置。
- PR 描述包含目的、流程、测试、风险、配置变化和回滚方法。
- 不用“AI 生成”代替代码审查；提交者必须能解释、调试和修改核心代码。
- 架构和业务路线变化更新设计文档与 `PROJECT_LOG.md`。

## 14. Definition of Done

一个任务只有同时满足以下条件才算完成：

- 功能形成真实输入到持久化/输出的闭环。
- 异常和失败状态可观察且可恢复或可重试。
- 自动化测试通过，必要时完成真实 MySQL/外部系统验收。
- 没有新增敏感信息、越权接口或无限资源消耗。
- 文档、接口和代码一致。
- 开发者能够解释设计取舍、事务边界和失败处理。
