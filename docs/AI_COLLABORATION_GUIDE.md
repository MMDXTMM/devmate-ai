# AI 辅助开发与项目归属规范

## 1. 基本原则

AI 可以提高开发效率，但需求、技术决策、验证和最终责任必须由项目开发者承担。

判断项目是否真正属于自己的标准不是“手敲了多少行”，而是：

- 能否画出架构和完整数据流。
- 能否解释核心表、接口和技术选择。
- 能否发现并修正 AI 生成代码的问题。
- 能否根据新需求定位需要修改的模块。
- 能否独立复现、分析和定位运行故障。
- 简历上的每个结论是否有代码、测试或数据证据。

## 2. 人与 AI 的职责边界

### 开发者必须主导

- 项目目标和需求优先级
- 业务流程和模块边界
- 数据库关系和接口契约
- 并发、事务、缓存和消息一致性方案
- 安全边界和权限模型
- 测试场景和验收标准
- 代码 Review、调试和最终合并决定
- 简历表述和面试讲解

### AI 可以协助

- 生成实体、Mapper、DTO 等重复代码初稿
- 补充测试用例和边界场景
- 提供多个设计方案供比较
- 解释框架 API 和异常日志
- 发现遗漏、重复和潜在风险
- 重构建议、文档整理和代码审查

比例不是考核目标。学习阶段建议开发者主导所有核心设计与关键逻辑，AI 主要承担模板、检索、初稿和第二视角审查。

## 3. 每个功能的协作流程

1. **开发者定义任务：** 写明目标、输入、输出、约束和验收标准。
2. **共同讨论方案：** AI 提供候选设计，开发者比较并决定。
3. **开发者先理解接口：** 明确模块关系和数据流后再生成代码。
4. **AI 辅助实现：** 优先生成小批量、可审查的变更。
5. **开发者逐个 Diff 审核：** 不接受看不懂的大段代码。
6. **执行测试：** 正常路径、边界、异常和必要的并发测试。
7. **记录决策：** 更新开发文档、ADR 和项目日志。
8. **开发者复述：** 能不看 AI 对话解释为什么这样实现。

## 4. 功能完成定义

一个功能只有同时满足以下条件才算完成：

- 代码可以运行。
- 自动化测试通过。
- 关键失败路径已经验证。
- 没有把密码、API Key 或本地数据提交到 Git。
- 相关开发文档已更新。
- 开发者能解释核心实现和取舍。
- 简历表述没有超出实际实现。

## 5. 简历规则

- 可以写“使用 AI 辅助开发”，无需隐瞒正常工具使用。
- 不把模型生成但自己无法解释的能力写入简历。
- 不写没有测量过的并发量、准确率和性能提升。
- 不写尚未实现的微服务、Redis、MQ 或生产级 ANN 向量数据库；当前只能准确描述为 MySQL 小规模向量适配层与混合检索。
- 每条亮点准备对应的源码位置、测试、运行结果和面试答案。

## 6. 文档维护约定

出现以下情况时必须同步更新文档：

- 项目主线或范围改变。
- 新增、删除或替换核心技术。
- 数据库关系发生变化。
- 关键架构取舍发生变化。
- 开发阶段顺序发生变化。
- 简历目标发生变化。

更新位置：

- 项目定位：`PROJECT_BLUEPRINT.md`
- 开发顺序：`DEVELOPMENT_ROADMAP.md`
- 数据模型：`DATABASE_DESIGN.md`
- 架构取舍：`ARCHITECTURE_DECISIONS.md`
- 重要变化摘要：`PROJECT_LOG.md`
